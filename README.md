## 1. 当前工作和边界

继续从公司已有资料收拢业务、页面、数据联系、权限、运行与验收；按已授权范围做必要隔离虚构验证。公司真实规则、正式开发、真实数据／生产、外发和部署各按对应授权及依据办理。持续推进不等于自动放行这些动作。外部技能和组件只取适合longshi的部分，不让它们反向扩大业务。

## 3. 命名与文档规则

- 新增资料使用 `YYYY-MM-DD-主题-类型.扩展名`，例如 `2026-10-25-业务员报价流程-访谈纪要.md`。
- 截图尽量带上模块、页面或动作，例如 `2026-10-25-报价审批-驳回原因.png`；批量连续截图可另加序号。
- 整理后的文字说明优先用 Markdown；原始图片、录音、PDF、Word、Excel 保留原格式。
- 原始资料保留原件。清洗、脱敏、标注或整理后的文件另存，并注明原件位置。
- 长期维护的总表采用固定名称，例如 `需求总表.md`、`待确认问题清单.md`、`项目决策记录.md`，在正文记录更新日期与变更。
- 避免使用“最终版2”“最新版最终版”等无法辨认状态的文件名。
- 文档内引用资料时尽量使用相对路径，方便整个项目移动或放入仓库后继续阅读。

每份分析或规划文档开头写明：日期、作者或整理方式、状态、来源。状态可用“待核实、草案、已确认、已替代”。关键结论在正文区分“事实、推断、建议”。

## 4. 从资料到施工计划

统一按以下顺序推进：

`原始资料 → 访谈或功能盘点 → AI 分析与技术调研 → 待确认问题 → 收敛后的需求和方案 → 施工与验收清单`

- 人工提供的原话与 AI 的解释分别保留；AI 推断需说明依据。
- 旧软件截图中出现的页面格式、字段、表格、筛选和状态展示，均按用户认可的参考样式提取与研究，不以“当前是否实际使用”为前提。参考格式与功能启用分别记录；新系统是否采用、何时实现，再结合 longshi 的需求确定。
- 调研资料中提到的技术栈目前属于候选方案，具体选型需记录理由及验证依据。
- 每项需求建议使用唯一编号，例如 `REQ-001`，记录来源、使用岗位、业务场景、优先级、状态和验收条件。
- 施工任务引用对应需求编号，并写清前置依赖、交付物和完成条件。
- 决策与变更统一记录日期、结论、理由、影响范围和依据，避免多个文档互相矛盾。
- 人数、部署位置、数据规模、审批规则等未知信息进入待确认清单，避免把假设直接写成既定需求。

## 6. 后续 EXE 软件开发目录

正式开发时再按选定技术方案建立代码目录，建议预留：

- `apps/desktop/`：Windows 桌面客户端。
- `services/backend/`：企业业务后端。
- `services/ai/`：AI 能力及工具接口；是否独立部署在技术方案中确定。
- `packages/`：确有共用需要的数据契约或组件。
- `tests/`：跨模块业务流程和验收测试；模块自身测试可随代码存放。
- `deploy/`：服务器部署、Windows 安装打包和升级配置。

EXE、安装包、构建缓存和大体积运行组件应通过构建或发布流程管理，通常不提交到源码仓库。发布产物的位置和命名规则在打包方案中确定。

业务数据由企业统一管理；AI 提取结果经校验和人工确认后，由业务系统正式入库。金额计算、审批、权限和核心业务应能独立于 AI 服务运行。
