| **S-B生效进展的局部卡点：G04** | 可靠订单／明细／阶段、数量含义、确认资格与该动作所需基线 | 当前可靠反馈、待核／缺历史可留；无依据累计／剩余／完成不出。只在涉及改价／接受时再引G01/G02，不普遍重走旧报价 |
| **按选定功能定稿：G05及G02/G06剩余细节** | 宣称正式统计／输出前需对应口径；真实试用前核目标环境／最低恢复／维护；特定审批按其动作核 | 普通查找、明确含义的简单清单／计数和合成对照早做；未选报表／远期模块细则后置 |

**结论：没有“六项全部解决才可开工”的总闸，也没有“G01以外都能默认”的通行证。** 正式开发仍由用户确认具体范围和执行授权；每个要生效的真实动作只核它依赖的最低条件。合成演示的假设角色和规则不转成真实授权。

## 3. 给老板看的量级：低置信、带前提的判断

以下是助手为决策给出的**粗略工程预算假设**，未由代表实现耗时、供应商报价或既有团队项目校准，不能当测量／行业统计／交期。所有“周”指每周约5个工作日，从范围、人员／环境资源明确且获准开始相应工作后算，**不是从今天倒数**；业务答复、排期、采购／网络批准等日历等待另计。

估算边界：一家公司、少量受控试用者和订单；先核有限角色／字段／资料类型和一种明确输出；S-A仅代表净尺寸板料及一种其他客户方式的已核场景，不包全部计价模式；不做全量历史迁移、旧库接入、自动微信采集、OCR／语音／Agent、所有旧报表或未知复杂打印。未入本批的旧功能继续按36组追踪。这是**量级假设，不是据此批准删减首批**。

资源假设：**1名能独立承担业务服务、权限、数据和部署交付的主要全时开发者**，另有可落实的兼职测试／运维支持，公司业务负责者可做短核／验收。上述能力可以由合适团队或服务商提供；并未证明公司现有这些人。四个AI聊天窗口不能直接折算四名全职工程师；仅实习生＋AI协作时，不套用下列熟练交付速度，学习／集成／技术审查需另计。

| 想看到什么 | 初步量级 | 明确的交付边界 |
| --- | --- | --- |
| S-C独立任务的可操作合成演示 | **约1—2个工作周**的目标窗 | 假人／假资料，用于核交互和方案；不是已具备真实权限、恢复和维护的可投用产品，也不是当前已经批准创建新站点 |
| 若另选S-C为更小的受控试用节点 | **约3—6全栈人周**；一名主要全时开发者可暂按约3—6工作周作预算起点 | 含该范围最小共享底座、业务、目标环境／负例／恢复和试用修正；需另确认范围。测试／运维人员工作量与可用性另列，不当免费并行 |
| 当前S-A／S-B／S-C三片段组成的受控首批 | **约10—18全栈人周**；同样资源条件下暂按约10—18工作周评估 | 含最小共享能力、代表报价／进展／任务及跨片段验证修正；不是完整36组替代，更不是全部基础系统／Agent交付 |

透明分解这笔10—18人周预算：S-C所需共享底座1—2＋S-C业务1—2＋该节点环境／负例恢复／修正1—2，合3—6；再加报价条件／精度／适用动作3—5、在途范围／更正2—4、跨片段集成回归2—3，合**10—18**。这是把粗估摊开以便质疑，**不是分解本身证明数字正确**；共享底座只计一次，不能再把3—6加到10—18上。合成演示可复用的量只有核实后才抵扣。

S-C适合作为较快的交互／工程试做，**不自动把用户目标改成先只交任务系统**。S-B未必最慢；报价种类和例外、框架适配深度、目标机／内外访问、当前规则与权限答复都可能改变顺序和区间。若要双人投入，须重排依赖和审查／测试责任，不把总时间直接除2；目前未取得第二开发者和稳定可用量，暂不编双人交期。

初建费用按当前节点比较：在途／任务／资料首节点用“6—12全栈人周×实际综合人周成本＋另列测试／运维投入＋获准基础设施／备份／分发和必要许可”；若选择原三场景一起交付则改用其累计10—18，不相加。按同一范围询价／比预算；当前没有实际费率、部署规模或服务商报价，因此不填虚构人民币总价。持续费用另算，不把开源当零维护费。后续用代表工作段的实际配置／开发／排错／验证记录收窄区间，而不是等所有远期细则齐了才第一次谈量级。

## 4. 谁维护：必须有承接，职责不等于三个固定岗位

用户本轮答复为**尚未确定**。下列是待分配的职责，不是任命某人；一个合适承接方可以覆盖多项，但需明确服务范围和公司决策权。

| 职责 | 谁来承接／应交付什么 |
| --- | --- |
| 公司业务与授权 | 公司指定的有权者决定规则／账号和业务验收；技术维护方不能自行批准经营制度或放开成本原件 |
| 应用与运行维护 | 待指定自有技术人员或服务商：版本／配置、故障定位修复、更新退路、数据库和原件备份恢复、证书／凭据及接手文档 |
| 云或基础设施服务 | 按实际采购范围承担主机／数据库等部分职责；租云主机／PaaS不等公司应用、权限与恢复无人负责 |
| 退出与接续 | 公司掌握必要源码／部署版本／资料与备份、账号所有权和受控凭据交接；维护人变动或供应商退出时有明确接手办法，不绑在实习生个人账号上 |
| AI协助 | 在当前授权内帮助研究、生成方案／代码和排查；不默认为24小时值守、服务合同、公司授权决定者或生产维护责任人 |

预算先比较：①有能力且有备份人选的自维护；②开发＋后续维护服务；③适用的受管服务＋明确应用维护承接。只比较这几种承接方式，不另搜几十个平台。由谁承接和服务时段／故障响应、升级／恢复／退出范围须与费用同时审，不能只比授权费。

没有维护承接时，继续研究／合成设计，不承诺真实投用或恢复时效；也不默认“既然开源，就让实习生自己顶”。本稿不是禁止公司自行建设，而是要求把实际运行责任纳入方案。

### 给技术承接方评估的最小要求（不由助手外发）

同一范围评估自有人员、开发＋维保、受管服务＋应用维护，避免只报授权费或把“包部署”当包维护：

| 需要书面说明 | 用来判断什么 |
| --- | --- |
| 本节点范围／适用假设／不含项，以及能配置／需扩展的部分 | 是否按同一个业务成果和数据边界估工，是否另算新需求而未说明 |
| 一次性开发费／测试部署费、持续维护和基础设施／许可／退出费用分别列 | 总投入及持续预算，不填本项目未取得的市场价格 |
| 谁负责应用修复、升级退路、数据库／文件／配置的备份恢复、故障和服务时段 | 哪些职责实际有承接，业务确认／授权仍由公司有权者决定 |
| 交付版本／源码及许可清单、部署和恢复说明、目标环境与验收记录 | 能否由另一技术人复现、升级或接手，不只交截图／开发机 |
| 公司控制的账号／资料／备份与受控密钥交接、数据导出／迁出和退出手续 | 不绑实习生个人账号，托管／供应商退出后仍可接续 |

当前没有供应商报价或技术方接单，上表不等采购、合同或直接联系他人的授权。若无人承接，仍可研究／明确合成演示，不能把责任空位隐藏为“AI自动维护”。

## 5. 技术路线改为受维护条件约束

Frappe框架＋独立应用和成熟组件组合均保留为**有条件候选**，不再默认自维护Frappe优先。优先比较：承接方是否熟悉、实际服务数与升级路径、需要改多少核心／业务规则、许可／费用、目标机和内外使用及恢复／迁出能力。自建组件也可能更难维护，不能反向宣称它必然轻。

尚无同设备／同负载／同数据量下的旧客户端和候选完整系统测量；客户端占用、服务器负载、依赖复杂度、技术人力和总费用分开。Frappe＋PG也不是当前已锁的组合，框架与具体应用数据库支持分开核。旧系统是否Delphi不决定这些答案。

官方[Frappe Docker说明](https://github.com/frappe/frappe_docker)和[部署方法](https://github.com/frappe/frappe_docker/blob/main/docs/01-getting-started/01-choosing-a-deployment-method.md)明确区分一次性演示、开发和生产；现成镜像／快速演示不是可直接交接的生产维护方案。本轮只读文档，没有执行安装命令。既有[内外部署研究](../../AI调研/技术调研/2026-10-26-公司内外访问与部署路线比较.md)第2／4节已写部分维护职责，但“有人承担”此前没有落实为人力／承接决策，这正是要补的缺口。

## 6. 当前接下来的工作顺序

1. 先审首批业务目标、上述量级／资源和维护承接选择；不让技术附件替老板决定值不值。
2. 保留已做功能／流程盘点；按三场景只核影响当前动作的最低真实规则／权限。重量舍入已待核，不催、不反复问模式。
