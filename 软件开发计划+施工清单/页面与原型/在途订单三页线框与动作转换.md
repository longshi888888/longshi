# 在途订单三页线框与动作转换

2026-10-27；revision 2；supersedes r1：按指定回读补草稿/订单与基线、变更动作分支、办理未明、视图滞后及来源依赖；r1保全项目外。1号；proposed。用户认可上一轮操作汇报并要求继续，本稿据[字段与动作候选r3](在途订单关键页面字段与动作候选.md)及[操作验收r2](在途订单操作与验收草案.md)展开。不是正式业务开发批准、已实现界面或公司制度；没有新组件运行。框内均为虚构演示，按钮表示候选动作。

## 1. 当前订单工作台

```text
┌ 当前订单 ─────────────────────────────────────────────┐
│ [当前订单] [待核需求] [需处理事项] [历史] [建立/接续*]   │
│ 找订单/需求 [输入内容]   筛选 [本人获准范围]            │
│ 数据时点：演示时点；现场情况以已确认记录和缺口为准      │
├ 已建立订单/需求摘要 ─ 已确认情况 ─ 待处理 ─ 最近更新 ─┤
│ 演示A/明细甲   甲范围4件加工   质量待复核  [时点]      │
│                已有确认       任务待验收               │
│ [打开订单] [留关键反馈*] [查看获准事项]                │
├────────────────────────────────────────────────────────┤
│ 其他范围：未获对应更新；不能据此认定其余6件未加工      │
│ 中途接续的订单：另示已知基线、接续前历史未齐提示        │
└────────────────────────────────────────────────────────┘
```

`*`动作按当前能力和对象范围出现；能查看不自动能建单或确认。查询失效／无权时不列隐藏订单、数量、负责人或内部原因。空视图写“当前获准条件下没有可列出的记录”，不推断全公司无订单。

待核需求可独立保存/查回，但不是已成立订单，不进正式订单统计；稳定内部身份不替成立依据。接续基线在详情保留覆盖阶段/范围、数量性质、已知截止时点和缺口；未核基线与首报兼容前不从零起算或直接相加。

“需处理”是工作视图，不替代各自状态；质量风险可与现有加工结果并列。暂停、取消、未判定完成等按适用规则呈现，不藏进“已完成”。列表只汇总获准字段，来源附件另核权。历史用途有明确入口，不能把旧记录混进当前合计。

## 2. 快速反馈与核对

```text
┌ 留关键反馈 ───────────────────────────────────────────┐
│ 当前上下文：演示A → 明细甲 → 加工范围甲（有据时带出） │
│ 若仅任务指向整单：提示“本次涉及哪个具体范围？”        │
│ 自由入口变体：关联未明·可先保存，不强迫选单             │
├ 本次变化 ─────────────────────────────────────────────┤
│ [甲这4件加工完成                            ]          │
│ [选文字/截图/音视频]  或直接简短补记，无须强制补图      │
│ 资料1：已保存  资料2：未收齐  [分别查看状态]            │
├ 必要核对 ─────────────────────────────────────────────┤
│ 说的是：[实际结果/计划/变更/异常/补充，按内容适用]      │
│ 数量及单位：[4件]  含义：[本范围累计等，有据才明确]     │
│ 发生时间：[已知值/未知]  来源：[亲历/转述/原文等]       │
│ [查看获准来源/差异]   不清楚处：单独待核                │
├ 办理提示 ─────────────────────────────────────────────┤
│ 内容：已核对@v2（示例）｜业务：待确认                  │
│ 确认前摘要：范围/阶段/数量性质/单位/所依版本（适用项）   │
│ [保存资料] [保存核对进展*] [本次适用主动作*]           │
│ “先保存”不代表正式确认；是否算上报按资料类别决定        │
└────────────────────────────────────────────────────────┘
```

该框一次展示说明职责，不规定所有人每次填这些项。可靠上下文和已核内容带出，只核本次差异；不涉及数量的沟通资料不硬填数量。关联不明可保存独立反馈，不逼人随便选一单。直接人工办理可跳过AI。

主动作随变化性质明确区分：实际阶段结果可为“核对并确认”；需求变更通常是“提交变更请求”，不因提交请求就改当前需求或加工量。变更生效另核适用权、规则、期望版本及影响；无须审批或同人能一并办理的情况可合并一次明确操作，但文案必须说明实际作用，不增加通用审批。

来源、数量含义和范围足以支持适用结果，且当前有权／规则／版本均满足时，才可办理“核对并确认”；无确认权者可办获准核对，不提供能绕权的按钮。内容尚有关键缺项时提示“核对进展已保存，仍待补范围/数量”；必要内容已核、仅待有权确认时才提示“内容已核对，业务结果待确认”。不能让后者重做已完成核对。

附件按件说明保存结果。只有本次正式结果实际依赖的来源已可可靠引用、该类规则满足，才可确认；不能引用尚未收齐的证据。无关附件失败不自动阻止另一条条件独立齐备的反馈继续，也不能把整批标全部完成。具体哪些来源必需依资料类型定，不统一要求纯文字必有附件。确认固定本次所用来源版本和核对基线，后到附件不自动追补为原确认依据；补充/替换按当前权、适用版本和关系另办。

### 提交中与结果未明时

```text
本次办理：正在提交 / 本次办理结果未明，正在查询
本次提交内容保持不变；已确认进度仍显示其原有效值与时点
[查询本次结果*]    [离开页面，稍后在待处理查看*]
不能把“没收到回复”提示成“肯定失败，请重新确认”
```

重复点击不产生新的业务操作。若还要修改内容，保留原办理线索，把修改作为后续草稿；不能用相同请求偷偷换正文。原请求是否已生效未明时，不把后续草稿再次确认成同一事实。离页或取消客户端等待不撤销已生效业务；“稍后可查”须以能持久登记／恢复本次办理线索为验收前提，尚未实现或验证。

## 3. 确认后查看

```text
┌ 演示A / 明细甲 / 加工范围甲 ──────────────────────────┐
│ 当前有效结果：甲范围4件加工结果已确认                  │
│ 适用范围/单位/确认时点：分别显示，发生时间未知不补造     │
│ [查看获准依据*] [查看更正/版本历史*]                    │
├ 需要区分的情况 ───────────────────────────────────────┤
│ 其他范围：未获对应更新      品质：待复核                │
│ 任务：待验收               通知：重试中/实际状态        │
│ 新反馈/新办理若仍待核：与当前有效结果分开列出           │
├ 后续动作 ─────────────────────────────────────────────┤
│ [补充反馈*] [申请更正*] [围绕此事下任务*] [按权提问]    │
│ 录错更正与后来返工分别处理；历史用途另选                │
└────────────────────────────────────────────────────────┘
```

业务明确成功但进度视图尚未追上时，单列“本次已确认，视图更新中”，标所确认办理版本及视图版本/时点；旧快照不标当前，不退回未明或重新确认来刷新。

收到明确业务成功结果才更新有效结果，查到既有成功也回到同一结果；较新结果已出现时显示当前版本，旧办理成功不把旧值复活。例：原办理回执为4件，后来已受控更正为3件，查原操作保留其回执身份，同时显示当前3及更正关系，不能用旧4回填当前进度。

一个结果可供进度、任务引用和老板查询复用，不多抄一份汇报表；反馈、批准、执行、验收、送达与已读仍各自成立。

按钮仅是入口候选，不给所有人默认更正／派单权。来源回看、历史查看、导出或AI使用分别按当前权限；进度可见不自动开放整件原文，历史也不永久继承原参与权限。

## 4. 动作转换：界面与服务必须对齐

表中是概念状态，非最终状态码。资料逐件保管、草稿核对、业务办理、现行结果和任务各有自己的状态，不串成万能“完成”。

| 前态／动作 | 条件与服务应核什么 | 返回后界面状态及可继续方式 | 不能做什么 |
| --- | --- | --- | --- |
| 有内容→保存资料 | 当前接收权、实际保管结果及逐件状态 | 已存/未收齐/结果未明分别列；可人工继续已存部分 | 上传完即声称整批已登记、已上报或正式结果生效 |
| 草稿→保存核对进展 | 当前核对权、草稿基线、实际已核与仍未知字段 | 可为“仍缺关键项”或“内容已核对，业务待确认” | 将两者都写“请重新核对”，或把已核当已生效 |
| 条件齐备→确认实际结果 | 当前主体/动作权、可靠对象、规则、来源依赖、期望版本及操作内容 | 提交中；服务明确成功才更新本范围有效结果，必要审计及版本一致 | 把变更请求/计划也当加工结果，或只靠按钮禁用防重复 |
| 需求变更→提交请求/适用生效 | 所改需求版本、差异、适用变更权/规则及依赖影响 | 待生效时当前10件与请求12件并列；只有明确获准生效才形成需求新版本 | 提交即改当前分母、自动增加加工量，或旧批准无条件沿用 |
| 发送前→取消本次拟操作 | 尚未发出业务请求；已保存资料/核对与本机未存输入分别处理 | 可以保留草稿或明确丢弃未存输入，不删已有保管记录 | 与发送后停止等待混同，或一个取消按钮删除原件/撤销正式结果 |
| 提交中→重复点击/重传 | 同操作身份与相同内容；服务侧防重 | 等待或返回既有结果；当前值以有效版本为准 | 新增一次确认/数量，或换键绕开原办理 |
| 已发→回复超时/离页 | 原操作线索保留，按当前权查状态；客户端未收到不证明失败 | 本次办理结果未明，可查原操作；可查询性持久恢复须专门验收 | 暂查无就换键重办；离页视作撤销 |
| 本次办理结果未明→查到成功/仍未明 | 当前可见权限、原请求绑定及现行版本 | 已成功则引用原结果/当前版本；仍未知保留未明 | 旧成功覆盖新值，或把无权读取当未执行 |
| 明确成功→视图未追上 | 办理成功版本/当前权、视图版本与读取时点分别核验 | 显示已确认及视图更新中，取获准较新视图后对齐 | 把滞后值标现在、显示失败或再确认一次刷新 |
| 提交中/未明→想改正文 | 原请求内容不变；修改另留后续草稿，不覆盖原线索 | 等原操作核明后，按适用修改/更正及当前版本办理 | 同键改正文，或新草稿暗中撤回原成功 |
| 冲突→核差异后继续 | 按权取得当前版本、保留本人输入；动作/规则重新适用 | 看到本次与当前的相关差异，明确重新办理或暂留 | 自动合并数量、偷偷换成最新期望版本重发、沿用失效批准或丢用户输入 |
| 无权/权限变化→重读或办理 | 服务端核当前主体和相应边界，不能信客户端旧许可 | 中性不可用提示；仅继续仍获准的能力，后台对账不等于撤销已生效结果 | 提示泄露隐藏订单/人员/数量，或模型代确认 |
| 已有结果→补充/更正/返工 | 同事实、录错及后来事件分开，核对象/版本/动作权 | 补充依据、受控更正或新事件各留关系；当前与历史分开 | 不同键一律累加，删历史，或把返工当录错 |
| 任意时点→旧提取/旧图到达 | 输入版本、草稿基线及实际时序；按权比较差异 | 旧候选保留，不盖较新核对或现行结果 | 晚上传=现场最新，或后台成功自动正式确认 |

AI故障不阻止仍有权且基础服务可用时的手工办理；业务服务／存储／授权不可用则说明实际受影响能力，不能用离线或AI补做正式确认。

## 5. 手机与电脑的同一规则

电脑可并列来源和字段；手机建议先固定订单/范围摘要，再显示本次变化，来源对照按需展开，最后是与实际状态相符的动作区。逐件上传状态和缺项说明不藏进悬停提示，重新进页仍能区分本机未提交、已存待核、已核待确认和办理未明。

这些是候选布局，没有固定像素、点击数或秒级刷新承诺。客户端复用同一服务规则；不同屏幕不能形成两套确认权或数量口径。
