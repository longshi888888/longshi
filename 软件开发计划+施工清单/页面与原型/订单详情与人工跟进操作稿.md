2026-10-28；revision 3；supersedes r2，r1／r2逐字保留项目外。设计仍为proposed；后续用户明确授权的整单文字小样已有限实现，见第7节。承接用户看过Bento小样后同意继续“订单详情＋人工跟进”的设计。本文把既有W07／W08／W09／W12／W14落到页面、少填方式和可检查结果；没有新增W编号，不改变受审首批r12或公司制度。原r1只完成资料对照和纸面走查；第1—6节保留当时的设计／提议状态，由第7节说明后续实际执行与仍缺部分。

## 先看这一页

**员工打开原订单，补一句发生了什么；老板在同一张单里看当前要求、有据结果和跟进历史。** 已知客户、订单和操作者由可靠上下文带出，员工不用再抄一遍。新消息保存成功，不直接改变正式加工数、交期或整单状态。

| 本次收拢的设计 | 员工／老板实际会看到什么 |
| --- | --- |
| 订单概况 | 当前要求、客户、责任及来源／版本；未知明确写未知，不能按录入人猜负责人 |
| 明细与范围 | 一个订单内各条材质／规格／要求分别看；能辨认哪条才关联哪条，同规格不自动合并 |
| 跟进记录 | 谁登记、原话或补记、来源性质、所述发生时间及登记时间；有据结果与新反馈分开展示 |
| 简短补记 | 默认只写必要内容；数量、范围、异常和原件引用按需要展开，不把整套字段变成每日必填表 |
| 填错和异常 | 纠正自己的说明留下原版本；更正正式结果、客户改要求、真实返工分别进入对应办理 |

三种状态不能混同：“这句话已保存”“有人反馈加工好了”“某范围已按规则确认完成”。普通备注可以只保留记录，**不要求每条跟进都审批**；需要改变正式结果的才办理对应动作，规则允许可由同一有权人一次明确完成。

## 2. Bento页面具体怎样摆

~~~text
┌ 订单／客户／来源与适用版本 ───────┬ 当前有效要求／交期 ──┐
│ 当前责任；已知内容与缺口         │ 有据结果及覆盖说明   │
├ 明细与范围：材质、规格、要求、数量及单位，各行分别看 ──┤
├ 跟进记录（当前获准范围） ────────┬ 补一条跟进 ─────────┤
│ 登记人／登记时间                │ 本次内容             │
│ 所述发生时间：未知／具体精度     │ 可展开：范围／来源   │
│ 来源性质；原文／本人补记         │ 可展开：数量／时间   │
│ 仅记录／待核或待处理／适用结果   │ 保存跟进             │
└ 原说明及修订／来源入口按当前权开放 ┴ 同次保存结果与查回 ──┘
~~~

这是信息布局草图，不是浏览器截图。沿已试的Bento分组／标题／用途样式，表格明细保留可对比的行列；窄屏拟按概况→明细→记录→补记重排，实际手机／缩放待验。来源和未知不为视觉简洁删掉，不增加虚构经营图表。

当前进展卡只读适用结果和覆盖，不把最新一句“做完了”当百分比。列表显示“最近登记”，不冒称“最近实际加工”；同时保留读取时点／适用版本，页面长时间未刷新须能辨认。某块读取失败只说明那块未取得，不把本来仍获准的其他块全部解释成无数据。

## 3. 谁填哪些内容，怎样减少员工负担

| 信息组 | 默认操作／候选约束 |
| --- | --- |
| 原订单／客户／已知责任 | 从有权且可靠的原详情带出；只读背景。登记人不自动变负责人，DEMO-A／B不是公司编号算法 |
| 订单明细及加工范围 | 已知可靠上下文带出并显示；员工可按获准入口选已辨认的范围。整单说明不自动覆盖全部明细；范围不清时标明，不让数字落到默认第一行 |
| 材质、规格、要求及单位 | 引用对应明细当前要求和来源；尺寸方向／单位未知不自补。件／套／重量及订单量／抽检量等分别显示，不沿小样整数件限制公司所有业务 |
| 跟进内容 | 本次至少有实际可保留的内容。普通补记可只写一句，不要求数量、百分比、附件或完整历史单据 |
| 来源性质 | 系统准确记录这是员工手工输入／摘录；若自称客户要求／他人转述，保留该性质及可用定位。登记人、消息原作者、实际执行人分开；不默认“本人亲见” |
| 所述发生时间 | 可未知；可只到日期或更粗的有据描述，按原精度保留，不强补时分秒／年份。不用文件mtime或登记时间代替 |
| 登记人／登记时间 | 服务按当前可信会话和本次成功登记记录，员工不手填身份；补录不会伪造当时已登记 |
| 数量（按需展开） | 先辨认本次新增／截至某时累计／某范围所述结果／纠错或不清楚，并保留阶段、单位及范围；无法明确时原话可按权留存，结构化量不进统计。不是每条必须选择数值模式 |
| 客户改期／改要求 | 保留新要求、来源及范围，当前有效要求并列，不能保存一句消息就覆盖交期 |
| 原件引用 | 资料入口建成后引用受控原版本；查看该订单／反馈不自动授予整件下载。当前小样无上传，不放假成功按钮 |

发生时间后来补充时，增加修订／补充依据及本次登记，不把旧记录改得像当时就知道。默认按登记新旧查看是候选交互；按发生时间查看时，未知记录独立说明，不能悄悄藏掉或塞到今天。

## 4. 按钮产生什么结果

| 动作 | 成功后可见／不会顺带发生 |
| --- | --- |
| 打开订单／明细 | 当前获准概况及适用结果，选中范围明确；可读不等可提交、确认或下载 |
| 保存跟进 | 可回查的一条记录、服务登记人／时间、原操作凭据及结果；提示“已保存跟进，未办理正式进度”。没有自动派事、通知、确认加工数或改变交期 |
| 查这次保存结果 | 当前获准入口下解释同次保存，不因超时就重建、换账号移存或拿旧结果覆盖当前操作 |
| 纠正自己的说明 | 指向原反馈及所见版、原因／修正内容，保留前版与修订历史；授权另核。不等于更正正式加工结果，也不重新产生一次业务数量 |
| 提出正式结果更正 | 指可靠原结果、范围、所见版及理由；保存请求不改有效值。G04／动作权／规则满足后才由人明确办理 |
| 记录后来真实返工 | 新事实和影响单独留存，不把原来真实加工抹掉，亦不按字面自动加减有效数 |
| 后续由此派事／引用资料 | 沿W10／W11分别办理、核权；任务可独立，无订单也可办，不把本页跟进保存当任务发布或文件已上报 |

不能辨认关联时，只有另有明确保存资格和独立入口才留待关联；无权或核权不可用的提交不自动转存其他目录／独立资料。对受限对象及来源存在性使用中性不可用，不泄露“隐藏了几条”。所有记录／范围／当前权与失败解释沿原数据r9，未定DDL或API。
