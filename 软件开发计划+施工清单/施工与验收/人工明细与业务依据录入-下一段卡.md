## 1. 先看员工要做的三件事



| 工作 | 员工最少需要做什么 | 保存后能看到什么 |

| --- | --- | --- |

| 录明细 | 找到可靠订单；按已知单据或说明填明细说明、明确的数量／单位，必要时标“资料还不完整” | 已存明细及其来源／登记人时间；加工、发出等未知继续未知 |

| 补进展依据 | 选可靠明细或范围，写“谁说的、什么情况”，数量性质／时间只填已知内容 | 一条可回查反馈；符合本次规则且本人有权时才可明确办理为相应结果 |

| 补发出依据 | 说明本次发的对象／范围、目的、来源及已知时间；有可靠计划才引用所指版 | 先可保存有来源的陈述；正式登记与计划／加工结果／签收／收款分别成立 |



不用AI也能完成这些人工步骤。附件不是每次必填；已知上下文由系统带出，不要求员工重抄单号、人名或完整历史。手工复述不冒充原作者消息，登记人不冒充实际执行人。



### 必须修正两项实验假设



1. **S01／S02不是公司逐件编号制度。** 旧小样人为给出了可区分的件。真实入口先以稳定明细身份、数量、单位和已知批次／范围表达；系统内行ID不等物理钢材编号。没有逐件或批次辨认依据，不能把“4件”自动生成的四个内部号当成四块实物已经识别，更不能据此证明跨次没有重叠。完整范围模型待实际资料映射，未知可先留反馈。

2. **实际发生不以先造计划为前提。** 当前shipment_sources为限定实验强制绑定计划版，尚不能覆盖无可靠计划的补录。后续来源入口应能按权保留独立陈述／待关联；无权时不能另找目录偷偷存。正式办理无计划实际是否允许及所需条件仍待依据，不强造排车或将送加工改称客户发货。



## 2. 第一段只补“人工建立明细”，不一次扩三套办理



先在项目外虚构副本，用一张**没有既存明细、结果、安排和实际记录**的新虚构单，验证正常页面从零建立两条明细并重开。沿已有订单入口产生该单；不清空原示例、覆盖已引用L1/L2或把旧S01/S02移到新单。账号及操作资格仍是明确实验设置，不叫员工自己配置权限，也不称真实G03通过。**本段仅空明细集合首次创建；已有明细的新操作明确拒绝、保本人输入。追加、修改、删除／重建另行设计，不由第一次创建入口顺便实现。**



| 界面／保存信息组 | 本段候选及限制 |

| --- | --- |

| 订单上下文 | 服务核可靠订单ID与当前查看／明细登记资格；带出已知要求版。看单、补跟进不自动等于可建明细 |

| 明细 | 员工填能辨认的说明；已明确才填材质／规格／数量／单位。第一实验例仅“件”，不把公司套／重量等排除出完整需求 |

| 不完整情况 | 数量未知与0分开；缺尺寸不编造。第一实验例用明确4件＋6件；其他未知字段可留待补，不自动由需求总量填满 |

| 身份／范围 | 服务分配稳定行身份，不用当前行号、相同规格或客户名查重合并。此段只建行与所述数量，不自动生成物理件跟踪事实 |

| 来源 | 记手工录入／摘录／转述性质、实际说明或可靠来源引用。引用原件时保指定版／位置并独立核权；可无附件保存独立说明 |

| 时间与回查 | 所述时间可未知，服务另记本次可信登记人／时间；一次保存及原操作绑定原内容，超时先查原，不换键重复建两行 |



**默认操作候选：**在明细区填两行→核对本次输入→“保存明细”→显示本次保存结果与已存明细。没有另加固定老板审批。保存仅表示该输入已登记，不能把输入内容认证为客户已确认、加工已完或允许发货。实际制度如另有审核，留对应规则位置，不暗设已完成审核。



两行作为本例一次保存；要么同次建齐，要么明确拒绝／未明查原，不显示假部分成功。原操作已成功后的合法查回／同键原内容重试必须先回原结果，不能因“现在已有明细”反认原次失败；查原仍核原对象当前权，不能泄露他单或旧权内容。首次创建的新操作以稳定订单为并发保护点或采用等效唯一性约束，不能只锁尚不存在的明细行。后续批量导入若采用逐行结果另行设计。4＋6与需求10在本例相符；不把“所有在途单明细必须立即凑满需求”写成公司规则，部分录入、数量不一致和未知须说明，不自动补差额或改原需求。



## 3. 数据与既有实验怎样衔接



从[数据边界r9](../数据与接口/报价与进度关键数据及办理边界.md)复用稳定身份、来源性质、当前权、原操作和历史职责；从[订单操作稿](../页面与原型/订单详情与人工跟进操作稿.md)复用未知／普通反馈分离，不另造通用“证据平台”。关系业务主库保存结构化登记、来源和历史；已有资料区保不可变原件版本。本段不新装依赖或选定正式底座。



本轮实际源码核对发现：detail_schema.sql只有detail_lines／detail_pieces等只读授予，行所述数量没有独立表达；现有读取用piece集合计件。因此**不能只加一个数量输入框、生成N个piece就称模型适合日常录入**。下一实现须明确“明细所述数量／单位”与“可辨识实物或批次范围”的区别，调整对应只读显示与写入资格；不得把所有实验表改为应用角色可任意UPDATE。旧逐件结果／计划／实际的来源边界保留，不在新行还没识别实物时强接旧结果。



后续进展来源先关联明细／可靠范围，保留本次／累计／更正含义；未明的普通反馈不生成首个结果头。明确首次结果与已有结果更正分开，遇到已存在结果不覆盖、不把首次登记变成第二次累计加量。实际来源与实际事件也分开，来源保存不更新改排保护事实；只有对应正式登记成功时按同次业务规则更新。新来源修改留前版，已使用版不能被改写；同内容可能是不同业务事实，不只按文字hash吞掉。

## 7. 下一段收窄：让某条明细找得到相关原话

**给使用者的一句话：**点一条明细，选择已经保存的相关跟进，明确保存关联；以后从这条明细找原话。无需重抄单号／聊天内容，保存关联不会把数量算成完工。这一步先解决“信息到底说的是哪一行”，不在缺G04时代公司确认加工完成。

### 为什么这样接

新明细已能人工保存，但普通跟进仍按整单保留。旧S01/S02结果与新ML行没有真实映射，不能把两套示例拼起来。先给已存原话补明确上下文，比直接把需求4件当完工4件更可靠。取舍依据见[明细／批次／逐件调查](../../AI调研/技术调研/2026-10-30-明细数量批次与逐件标识取舍.md)及既有订单操作／数据边界。

示例仍全虚构：本单甲行4件、乙行6件，先用普通跟进保存“甲行加工已结束，数量还没核”。有权人把这条原话关联甲行，系统记人工指定的关系、所指原话版、操作者和时间。甲行需求仍4，正式加工结果仍未知；不是因为原文提到“结束”就确认4件，更不会同时改乙行、派车或结案。

### 拟定最少操作和数据职责

1. 从当前获准明细发起，带出可靠订单／行身份及所见首次集合版；不让员工键入系统ML号，也不用界面第几行替代身份。
2. 只列当前有权查看、在同一订单内的已存跟进，展示完整原话及来源／登记信息。可选取已有内容，不再复制成另一份“权威原文”。无可靠对应的“这批好了”仍可在原跟进里保留未关联，不能默认甲行。
3. 明确保存一个“人工指定的来源关联”，保订单／行、反馈身份／固定版、关联人／时间和原操作。该关系只说明人指定了上下文，不认证原作者、消息内容真实或工序完成。原文、当前有效结果和本次关联各有自己的身份／状态。
4. 从该行的相关来源区读回，并可打开所指原跟进版；返回仍核当前权。关联可见不授整单／附件下载、任务接收也不自动授关联／结果办理权。第一实验拟只允许演示创建者关联自己的跟进，真实G03另核，不把这一实验分工推广为公司制度。

第一段只关联已有跟进，一次选一条明细；不同时实现新建原话、解绑／改指、批量、跨单或正式数量。若以后从明细直接补一句，须复用同一跟进主记录并明确同次保存，不能靠两次接口调用假装原子完成；本段没有这一新建能力。

同一反馈固定版与同一行的同类引用是同一条关系，新键重复引用可返回已有关系，不能产生两份数量；不同反馈即使文字一样也可能是不同来源，不按全文hash吞掉。改变所指行／原话／版不当成原操作重试。源码中的同单组合约束与当前权限要一起满足，数据库FK存在不代业务授权。
