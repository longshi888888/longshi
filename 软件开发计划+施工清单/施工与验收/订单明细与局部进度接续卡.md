# 下一段：同一订单的明细、局部进度与待核反馈

## 1. 解决什么工作

老板或跟单打开同一张在途订单，能分清：哪些明确范围有有效结果，哪些只是有人反馈，哪些仍未知，以及这次安排指的是哪几件。员工不抄整单，不要求每条聊天入库，不自动多加审批。

先补同单明细/范围和进度的只读接续；正式确认、更正及实际发货分别按后续具体卡和对应授权执行。不把旧PC-A、PD-W/J凭客户名或标题挂到当前O-ID，不把“已有独立实验”当已整合。

## 2. 同一张单具体怎么摆

| 页面区域 | 显示内容 | 不应被混作什么 |
| --- | --- | --- |
| 订单概况 | 当前可靠O-ID、需求量、交期及未知 | 需求10件不是已加工10件 |
| 明细及本次范围 | 有据明细身份、单位、范围中的明确件身份；缺规格/分组标未知 | 同规格、同客户、同数量不能自动合并；不拿供应商、车次当订单身份 |
| 当前有据局部结果 | 阶段、适用范围、有效数量、结果版和来源；发生/登记时间分别显示 | 一条局部结果不换算整单百分比；不能据它断言其余都没做 |
| 待核反馈 | 原话/人工补记、可靠或待核关联、处理状态 | “加工好了”不自动生效，不新增正式数量、不冲销旧结果 |
| 本次安排 | 沿现有安排引用明确范围，保计划与当前依据 | 已排2件不等已发2件；进度更正不静默改旧安排/历史输出 |
| 任务和资料 | 按现有当前权与固定引用版回查 | 任务回复不等生产确认，资料关联不授原件或整单权 |

这是订单页的新组织建议，未把全部生产工序、质量检验、成本/利润或排程优化塞进本段。

## 3. 限定合成例与数据归属

沿S6正常停止副本中DEMO-SAME-01实际生成的O-ID，需求10件、现有任务和资料、S01/S02首次安排原样保留。**新实验若需明细分组，须另外明示为合成设置后取基线**，不回写原S6或倒认公司实际规格/分组。

建议仅设演示明细L1：S01—S04四件，L2：S05—S10六件；规格、重量未知。建议预给一条明确标为夹具的加工局部结果：仅S01/S02有完成依据。其余加工状态未知，检验/实际发出未知；不能显示“还剩8件未加工”，也不替换原固定甲乙/丙丁/4→3案例。

订单身份由orders原记录负责；明细/范围必须可靠归属该O-ID；阶段结果和反馈分别引用相应范围、阶段、单位与源版；安排沿自己的原版/逐件范围，不由最新进度字段反写历史。本段只收拢归属，不提前冻结DDL/正式API。

公司的G03/G04仍待依据。演示资格/完成依据若预置，必须标为虚构，不能因此开放真实确认。不能确认对象、范围或性质的文字先独立留存/待核；有权的其他工作仍可继续。

## 4. 下一段必须观察的六件事

| 场景 | 应看见什么 | 当前状态 |
| --- | --- | --- |
| C1 同单回查 | 原O-ID下找明细、局部结果及安排范围，跳转回原单；不借旧PC/PD名字对单 | D2普通页面同单读取；仅预置明细/结果 |
| C2 反馈不变正式结果 | 员工提交“这批好了”或独立任务回复，仍只属反馈；未知不变0，不做整单累计 | D2普通补记保存/重开及API对照，未改结果 |
| C3 范围/阶段/单位核对 | 本单加工的2件不加到别单、检验或公斤栏；重叠件不重复计，覆盖不完整不报全单值 | D2接口专用库有限反例，非全单位支持 |
| C4 进度与安排各保含义 | 当前局部结果即使变更，旧2件安排仍保原版；需要核查时提示相应范围，不能自动判整单不能发/取消安排 | D2两隔离夹具只读对照，非UI更正；真实条件未核 |
| C5 按当前权读取 | 可看必要任务不授整单/明细/结果/原件；进度块不可读不清其他独立可靠内容 | D2普通顺序撤权/切号与API限定核对，非真实G03 |
| C6 历史和退出保护 | 所有预置/新操作/只读分别列出，原行、原件和源副本不变；有限实验正常结束 | D2前后保护/冻结及正常退出已核，查看副本另计 |

新运行前先固化合成输入、隔离源/资源、可读接口与当前角色范围，按这六项一次收尾。正式办理不在本段顺带增加；不以公司暂缺为理由停掉只读设计，也不以本卡放行生产。

C2未来只经既有人工整单补记/任务回复入口记录原话，不在本段增加阶段正式确认命令。C4先准备两份明示不同结果状态的隔离夹具，用只读查询观察当前/历史和安排的呈现；状态差异来自实验设置，不能声称员工从普通页面完成了更正。若要实际确认/更正，另按具体范围和对应依据办理，不借C2/C4场景文字扩大本卡。

## 5. 已查资料与后续顺序

复用[订单进度职责](../../AI调研/技术调研/2026-10-26-订单进度权限与一致性职责补查.md)及[关键反馈可信链路](../../AI调研/技术调研/2026-10-26-关键反馈到订单进度的可信链路补查.md)，结合[S6范围/方法](../../AI调研/技术验证/2026-10-30-同一订单接续与切任务保护阶段记录.md)。不新选平台或安装工具；已有PG/FastAPI只作实验环境，不认定为生产选型。

顺序：**同一订单明细/局部进度只读接续 → 条件明确的正式结果办理 → 本次安排及适用变化核查 → 实际发出/物流/签收的具体方案**。报价/客户经营等完整范围仍保留，顺序不当新首批范围批准或工期承诺。

## 6. 本轮停后快照核对：下一段具体缺哪里

只读S6正常停止后保存的after.json中same_ui表快照，没有请求当前服务或新查数据库。实际本单为需求10件、1条跟进、1条订单资料引用、1条S01/S02的2件安排；安排的order_id与原orders一致。当前scope来源只有source_ref、逐件身份、单位、预置eligible/revision，same_ui没有已保存的明细/生产进度结果表。不能把eligible=true当本单加工完成记录，也不能把它当真实公司的交付放行制度。

因此接续卡新增部分必须有明确归属和有限读回证据，不能仅把旧进度页加一个链接就称本单贯通。原S6业务行保持；若用新虚构明细/结果必须分别标注预置与普通办理。定位与源范围存项目外flow-consolidation-20261030/s6-saved-identity-audit.json。本段是保存快照结构核对，非本轮新运行或公司规则确认。
