## 给使用者的一句话

员工照常补关键情况。有明确对象、范围和依据，并且本人有权时，可以一次明确操作把这一局部记为正式结果；只有“这批好了”而没有明确范围时，继续作为反馈保留。是否另需审批由公司实际规则决定，不默认多一道老板审批。

## 沿用哪一张单，先做哪一次办理

仍用原可靠O-ID的虚构副本，L1/L2、逐件身份及原S01/S02安排保留。不把旧PC-A/PD-W凭名称挂过来，也不复制运行中的查看库。拟从正常停止D2副本开始，实验设置和普通办理分别取基线。

建议第一步只做“加工局部结果更正”：预置DR-01 v1=S01/S02及一条明确说明“原记录中S02误计”的反馈，明确演示办理资格和适用定义；普通页面选择该反馈，对回本单/L1/加工/件，明确更正为S01。旧v1保历史，新v2代替该结果的当前引用，不加成3件、不推整单完工、不改任务回复或原安排。**这不验证首次确认原2件，也不把真实返工当录错。** 首次确认和返工按不同案例另验，不能一个“更正”按钮包办。

本轮D2另一库的预置v2只证明只读呈现；下一段若获相应具体执行范围，才从普通页面办理此变化。当前网站尚无该按钮/命令。

## 界面和数据怎么接

1. 在本单明细区进入“核对局部结果”，带出可靠订单、明细、阶段、单位、当前结果版和可读依据。来源标题/同客户不能代关联；来源读不到就不显示旧原文。
2. 人核对明确件身份、变化性质和理由；发生时间未知可明确留未知，系统另记办理时间。不能用系统时间冒充实际加工发生时间。
3. 业务服务核当前读/办理资格、规则定义、来源绑定与是否已办理、当前目标结果版；一次事务保存新结果、凭据、替代关系与原操作记录，推进对应结果头。不顺带改订单交期、任务、资料或出货安排。
4. 返回本单当前结果、旧版和原安排的核查提示。核查是提醒相应范围，不在此决定整单能否发货；原计划输出/人工通知不静默重写。

“同一次提交只成功一次”、版本保护与历史回查可复用[独立H3实测](../../AI调研/技术验证/2026-10-29-局部结果普通更正与历史回查实测.md)的设计和失败经验；旧实验用progress_cases，当前用可靠orders和detail对象，必须重新核映射和当前权限，不能只挂一个旧路由就称同单办理完成。

## 下一次运行必须取得的具体证据

| 检查 | 应得到的证据 |
| --- | --- |
| 普通办理与重开 | 明确更正S01/S02→S01，重开当前1件；旧2件及来源/人/时间/替代关系可查 |
| 未明结果查回 | 已提交但回复超时，保留原操作和内容；查原结果或原内容重试只取同一次成功，不再写一版 |
| 拒绝混办 | 新键旧所见版、同键换内容、他单/明细/阶段、非件单位、未知件、未明范围或重复处理来源均不写正式结果 |
| 权限与原操作 | 先核原操作真实范围，再比键/动作/内容；失办理权但仍有读权可只读查回，失读不可借旧键探查；任务接办不自动授办理权 |
| 原安排与未知 | 原两件安排不改；S02需核当前依据，实际发出/全单剩余仍未知，原历史产物保留 |
| 原数据及退出 | 原单、任务、资料/字节、其他结果和未触范围保留；源冻结/夹具/普通操作分开列，正常停本轮资源 |

只支持本例明确件，重量/混单位/多阶段返工不靠默认值放行。真实开放前仍需实际岗位的完成/更正依据、授权和目标环境验收。本卡不扩大真实访问、安装、发布、Git或关机范围。
