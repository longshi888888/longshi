## 3. 第一步：先把公司讲清楚

首轮只围绕下面三个主题逐步沟通，不一次抛出整份问卷。已有资料能回答的内容先引用；出现冲突或缺口再补问。

当前先按用户要求完成旧软件及已有资料研究，再结合具体页面和案例进入以下主题，不用这三项通用问题替代材料阅读。

1. **经营与客户**：longshi 主要提供哪些产品或服务？典型客户是谁、买来做什么？公司在供货、生产、加工或其他环节中实际承担什么？
2. **人员与工具**：你目前负责什么？一笔业务实际经过哪些岗位，每个岗位用什么工具记录和交接？
3. **真实问题与目标**：最近哪件具体工作最费时间、最容易出错或最难追踪？当时怎么处理，造成了什么影响？改善后希望能观察到什么变化？

不要求公司先准备完整报告，可以先口头讲，由我整理成文字；不确定的信息明确记为待核实。

## 4. 真实案例的访谈提纲

访谈目的：了解一笔业务实际如何发生，为流程、字段、权限和第一版范围提供依据。先说明此次是了解工作现状，并约定可用时间；若需要录音，先征得受访者同意。

按真实经过逐步追问，相关环节不存在就跳过，不预设 longshi 一定涉及库存、加工、生产、外贸或多级审批。

1. 最近一笔已完成业务是什么，客户从哪里来，最初提出了什么要求？
2. 谁确认产品和规格，依据什么资料，信息不全或有变化时如何处理？
3. 价格和交期由谁确定，依据什么规则，什么情况下需要他人审核？
4. 客户确认后，如何安排后续工作？实际涉及采购、加工、库存或运输中的哪些环节？
5. 每次交接传递什么信息，存在哪里，下一位经办人如何知道轮到自己？
6. 交付和收付款实际如何进行，谁确认结果，哪些记录表示业务结束？
7. 对照一笔异常业务：具体在哪一步偏离正常流程，谁发现、谁处理、留下了什么记录？
8. 这次最费力的部分是什么，曾经怎样尝试改善？还有哪些相关人员或证据可以补充？

追问重点是“最近一次具体怎样发生”“能否举例”“下一步是什么”“依据在哪里”。先了解现状，再讨论方案。

### 访谈记录字段

每次访谈按实际内容记录，不为补全模板编造答案：

- 日期、受访者及岗位、记录方式、案例标识（避免不必要的个人敏感信息）。
- 要完成的工作、触发条件、参与岗位、实际步骤与交接。
- 当前工具、输入输出资料、来源路径、适用的规则与例外。
- 原话或已核实事实、痛点与影响；耗时、次数、金额等无数据时不填估算值。
- 希望改善的结果、当前投入的时间与成本。
- 意外发现、推断、待确认问题、下一步核实事项；负责人和时间未知时注明未知。

- [ ] 页面草图能按真实案例走通，主要操作和信息展示符合实际岗位工作。
- [ ] 技术及部署方案基于真实使用条件；仅对影响决策的不确定性做必要验证。
- [ ] 开发任务有需求来源、依赖、交付物和验收条件，估算未冒充确定承诺。
- [ ] 遗留问题标明影响和处理安排，范围或技术方向变化有记录。

## 7. 后续开发顺序的形成方式

在需求收敛后，先完成客户端、登录及权限所需基础，再选择最有价值的一条真实业务流程贯通数据、附件和操作记录。之后按依赖增加其他能力，最终完成 Windows 安装、升级和试用验证。

现有资料中的“客户—询盘—报价审批”可以作为第一版候选，但尚未确定。用户已明确数据中心、不同输入的文本提取、关键词与向量检索、按需仪表及AI只读/JSON交互方向；具体阶段安排与任务管理、培训等能力的取舍，要结合实际价值、依赖和可行性核实，不按技能模板或原始功能清单机械安排，也不提前将AI及检索整体推到后期。

每天结束可整理新增事实、已作决策、未解决问题和下一步行动；用户要求“下班提交”时，按 README 的流程提交并推送 GitHub。
