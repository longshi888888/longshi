# 首批权限与授权候选

2026-10-27；revision 1；1号协调；supersedes：无。proposed／权限设计，不是公司已批授权表、账号配置或产品验收。适用首批在途订单＋任务＋资料及同条件清单，完整旧功能仍按原批次。

## 0. 先看这几句话

默认查看方向“员工自己／主管本部／老板全公司”继续保留；**能看、能反馈、能正式确认／更正、能打开原件、能导出是不同能力**。具体对象、字段、例外及各动作由谁办理尚待依据，不从岗位名称算出已授权结论。

任务不能只让原作者看，否则员工收不到老板派来的事。建议另有“当前获准接收／处理本任务”的必要内容范围；这是候选协作规则，不自动开整张订单或全部附件，也不把它称公司已批准的例外。发布者能看，不等能把内容转给任意人。

员工尽量只留一次关键变化；正式生效条件、当前资格齐备时可同人一次明确办理，不统一增加主管／老板复点。AI无正式业务写入／确认／审批权。

## 1. 已知方向和未定制度分开

| 依据层次 | 当前沿用内容 | 不能据此推出什么 |
| --- | --- | --- |
| 用户要求／共同约定 | 老板与员工区分、默认查看方向、内外均可用、AI不直接改正式业务；任务可由他人下发 | 不能把全公司查看写成老板所有动作均有权，或员工曾提交就能永久读整单 |
| 已读旧页面／资料摘要 | 人员、部门、角色成员、业务员及部分授权入口；按原报告层次复用 | 未见完整有效策略；角色名、菜单勾选、业务员代码不证明实际字段／动作权限 |
| 助手候选 | 以下动作拆分、任务必要内容关系、逐请求核当前权、给定允许／拒绝例子 | 不是已访谈全部负责者、已授账号、权限库已采用或完整公司规则 |

## 2. 一次操作至少核哪些维度

可信当前账号／会话→具体对象及可靠关系→本次动作→可见字段／来源存在性／整件范围→当前授权及所见业务版本。身份和允许结果不让客户端、模型或一个“我是主管”字段自报。

“自己／本部”按何种对象关系和时点计算仍需细化，不能仅按创建人或当前部门一刀切。客户归属、订单责任、任务接办、数据访问及统计归因分开；可靠关联只证明对得上，不代授权。跨岗代录留实际来源／记录人，不冒成原岗位确认。

不同授权视图可以不同；一致是同许可、条件、时点和字段含义下可对账，不是强迫所有人看一样的名单、明细或原件。

## 3. 首批要分别设置哪些能力

下表是待落到规则的能力清单，不给任何真实岗位打“全允许”。实际办理人和对象／字段范围由相应依据核定。

| 能力 | 候选授权应限定什么 | 不能顺带获得什么 |
| --- | --- | --- |
| 查当前单／明细／清单 | 当前获准订单、范围／阶段、字段、期间／查询条件及历史读取范围 | 不因看摘要就开成本、所有明细、来源存在或整件／输出 |
| 补本次反馈／代录 | 允许提交的对象／范围和内容，可靠上下文及来源性质；可独立待核 | 不能改当前要求、确认别人的阶段、让反馈自动生效；代录不伪签来源 |
| 正式确认／更正／改要求 | 分别核该对象／阶段／动作资格、完成依据、所见版与受影响范围 | 提交权不代确认、更正、审批或检验；不能覆盖全部工序或删除历史 |
| 发布任务／定接收范围 | 发布者当前资格、本版内容和拟接收人是否获准接收这些字段／说明 | 不能凭勾选某人制造其读取权，或将混成本原件直接带入通知 |
| 接任务／回复本人事件 | 有效且获准的接收／处理关系、必要要求、期限／本人责任及可回复范围 | 无安全关联摘要时只给获准独立说明；不自动开订单详情／他人历史／原件，收到不代验收 |
| 转交／取消／改期限／验收 | 各动作资格、当前对象和版、生效范围／时点；拟变化保留待处理 | 不能未生效先换责任，已读不代接办；普通回复不授这些动作或反写进度 |
| 保管／整理／业务关联 | 上传、人工注记、添版、改关联各自范围，可靠引用及所见版 | 原件保存不代上报／确认；关联不扩大整件权，注记不盖字节或正式业务值 |
| 看来源／原件／下载 | 来源存在、标题／片段、预览、指定字节版本和整件分别核 | 不能从订单／任务查看权推全部文件权；元数据也可能受限 |
| 查统计／生成及领取输出 | 汇总和明细各自范围；请求、后台生成、领取、重开均核实际请求人当前权和产物字段 | 汇总不自动开明细，产物不能静默带受限行列／原件，服务账号权不代请求人 |
| 管账号／权限配置与技术维护 | 维护动作、可配置范围及实际接触数据／备份／凭据的路径另核，留变动依据 | 应用账号管理不自动授业务确认／成本读取。页面分权也不能证明有服务器／备份访问权者物理上无法接触原文 |

账号、员工／部门／业务员、记录人、当前处理人不是同一个身份字段；停号和业务交接分别办理。技术维护需纳入实际接触范围和交接约束，不默认由实习生／AI承担或据本表授予生产访问。

## 4. 同一边界怎样覆盖所有入口

内部记录区分拒绝、依据未定、不可核和冲突；对外提示按存在性边界保持中性，不必告诉无权者“某条记录存在但你无权”。在已核授权范围内确无匹配可正常返回该范围的0；系统另有隐藏记录不向他泄露，也不把核权失败伪装成这个合法空结果。

- 列表、详情、搜索候选／片段、通知标题／预览、统计、原件、输出和旧操作回查都核当前人及相应范围；只藏按钮不能控制服务／直链。
- 获准读取正式进展、但来源读取被撤去时，分别按各自当前权返回：可保留另有权限的结果，不夹带已撤来源正文／名称／数量；撤权本身不删除或无条件回滚已成功事实。
- 来源／片段进入重排或未来AI前就限定，输出领取及历史内容重开再核；后台处理者能处理原件不代表请求人能看全部。AI只生成获准候选或读分析，正式业务仍由明确人动作办理。
- 原操作身份只用于查当时办理，回查／重试核当前权及主体／动作／目标／输入和所见版绑定；读不到原详情不证明没执行，不换键盲重做，不无条件重放敏感旧回执。
- 明确无权、授权依据未定、核权暂不可用、版本冲突和真实空结果分开；受影响读取／正式动作不沿用旧允许，也不冒作“0／不存在／已完成”。具体客户端保留草稿按获准边界另定。
- 转交／撤权／调岗／停号后读历史按当前规则；提交与权限变化的排序／原子边界按数据r5§6设计并待实现验证，不承诺零窗口或靠缓存实现撤权。
- 在隔离环境恢复旧库／策略／索引／队列并核查后，对外开放或重放前核当前授权与原操作结果；未核清保持相应能力受控，不复活旧权或盲重发。已交付明文副本不能靠服务端撤权收回。

## 5. 给开发者的固定反例：只预给演示资格，不创建账号

下列各行独立给定允许／拒绝条件，沿原两单／独立事项／资料输入，不组成公司新角色表。全部是未来检查，未运行权限引擎、数据库、下载、通知或恢复。

| 演示条件与动作 | 将来应看到什么 | 必须阻止什么 |
| --- | --- | --- |
| 演示人可读单甲范围摘要、可留更正反馈，无正式更正权 | 查原4及待处理3，反馈可回查；正式办理给受控结果 | 用提交／看见按钮把有效4改3或加7，猜对象标识越范围读写 |
| 演示人另有范围甲更正权且预给依据／版齐备 | 明确办理后局部3，原4及替代保留；任务只引用 | 其他工序随改、任务／整单自动完成或来源原件自动开放 |
| 演示接收者获准看／回复独立任务必要说明，无关联订单详情／原件权 | 找到已发布本版事项，回本人反馈；安全独立说明可办理 | 要求他先成为原作者；接收人勾选绕授权、任务链接开整单或复制受限成本 |
| 演示人有正式结果查看权，原件／来源元数据权已撤 | 只返回仍获准结果和当前允许信息；受限原件出口不开放 | 删掉有效进展、旧搜索／直链／通知预览暴露文件名数量或正文 |
| 演示输出生成时有权，领取前相关权已撤；或恢复了旧策略 | 领取／重开按当前权处理；隔离恢复核当前授权后开放获准部分 | 为页面对账保留旧权，旧队列／回执无条件放数据或重执行业务 |
| 演示事项原负责人拟转他人未生效，随后原人撤权／旧请求晚到 | 责任按已生效关系，旧作者保留；当前无权请求不能借旧版继续改，原操作是否成功有受控查回 | 已读当接办、申请提前转责任、无权查原件就判操作未执行并另建一次 |
| 受控核权暂不可用；另一个分支明确获准范围内确无匹配 | 前者说明受影响能力暂不可核，后者才给该获准范围真实空结果 | 把核权失败报0／无订单，或用旧权限／模型猜允许继续读取 |
