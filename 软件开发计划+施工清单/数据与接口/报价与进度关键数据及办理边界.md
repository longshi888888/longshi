### A. 哪些是主记录，哪些只是页面引用

| 员工看到什么 | 主记录需表达的信息组 | 谁录入／改变，其他页怎样用 |
| --- | --- | --- |
| 当前订单及范围 | 稳定订单身份、能识别的单号／客户线索、当前要求版本、已明确责任；可靠明细／范围身份、阶段／数量单位、已知基线及缺口 | 获准人登记／接续当前资料，不捏造旧报价／历史；变化按相应动作生效，清单读适用内容。单号／界面行号不代明细身份 |
| 本次反馈／变更／更正请求 | 内容及来源性质、可靠订单／范围、所见依据版、已知数量及本次／累计／更正含义、发生时间及未知、登记人／时间；更正才指被改结果 | 有本次提交权的人留已知内容，可待关联／待核。人工复述不冒作客户原话，保存不替换有效量；未知不补0或文件时间 |
| 有效结果及历史 | 适用范围／阶段、值及单位、来源反馈／证据、办理依据／人／时点／规则与适用版本；更正的原结果／替代关系 | 有权者明确办理，系统按当前权／版本／规则保存；可同人一次办，不默认主管再批。其他页引用，不各自改另一份完成量 |
| 任务及逐人事件 | 持续的事项身份、草稿／发布要求及接收范围版本、已生效当前责任／期限和待变化；实际人对应回复／送达／阅读依据及所指内容版 | 发布、回复、转交／取消和适用验收分别核权；转交不另建同一任务、不改旧发布快照／作者。无阅读依据是未获依据，不硬判未读 |
| 原件、文字及目录 | 文件／资料身份、不可变字节版本；清单版本及逐项路径／空目录／状态；独立文字或人工注记的来源性质、必要版本／位置和逐件结果 | 有保管／整理权的人存和补记；注记不盖原字节，原件／提取／引用各有状态。文件已存不等关联、上报、确认或整夹成功 |

### B. 订单、事项与依据怎样连

~~~mermaid
flowchart LR
  O["稳定订单／当前要求版本"] --> S["明细／范围与已知基线"]
  S --> F["本次反馈／变更或更正请求"]
  V["原件版本或独立文字来源"] -.依据引用.-> F
  F --> H["有权者按本次规则明确办理"]
  H --> R["适用结果与替代历史"]
  R --> Q["获准订单详情／跟进清单"]
  T["同一任务／发布内容版本"] -.可靠时关联.-> S
  T --> U["逐人事件／已生效责任／待处理变化"]
  R -.只读引用.-> A["获准相关事项页"]
  U --> A
~~~

箭头只是联系，不表示每项必须有订单／附件、关系都一对一或按箭头多轮审批。任务可独立；一项涉及多单／多范围时明确覆盖，不能凭客户同名／规格近似猜关联，具体分配待实际规则。

任务引用进度身份／适用版本，当前进度由业务服务返回有效版；发布、已读、回复、验收或责任变化本身不反向改数量／确认／整单状态。反馈若符合正式进度条件，可由有权者明确办理并复用结果，不只凭文字“完成”生效。通知重试指同一原事件和实际接收者，不新增业务事实。

### C. 文件身份、版本、目录与业务引用

~~~mermaid
flowchart LR
  I["文件／资料身份"] --> V["不可变原件版本"]
  L["目录清单版本"] --> E["逐项条目：路径／空目录／状态"]
  E -.成功项才引用.-> V
  B["可靠业务对象／范围"] --> X["业务引用关系"]
  X --> V
  X -.目录资料时.-> L
  N["人工注记／修订与来源性质"] -.有依据时指版本／位置.-> V
  P["一次办理身份"] --> Z["逐件实际结果／未明待核"]
  Z -.有据保存后才对应.-> V
~~~

- 文件名只是展示；改名／移动不换原字节，新字节另留版本。“刚上传”“同名”“业务有效版”分开。同一版本多处引用不共享整件权；改关联不自动改字节、扩大权或删除其他有效引用。
- 目录条目可先记失败／未明和空目录，未枚举完不当完整总数；成功登记后才有据连保存版，不能先伪造成功版本／关联。字节接收、登记和关联不假装一个跨存储事务已完成。
- 人工注记保留原作者、来源版／位置及原文、摘录、复述或推断的性质；独立文字可无附件，不强制造文件。旧提取迟到归原输入，不盖新字节／人工修正或当前业务依据。
- 原操作回查核可信主体／动作／目标／输入及所见版绑定与当前权；旧回执解释当时结果，不能把已更正当前值恢复成旧值。结果／文件存在也无权时，不泄露名称、数量或原操作存在性。

恢复按既有契约核业务记录、被引用原件／目录版本、人工修正、配置及当前权；图中有连接不等引用完整、跨存储原子提交成立或产品恢复通过。

## 当前补充：数据怎样存、怎样接交付与款项

用户询问存储方式，本节记录助手当前建议，不等于已选数据库／云位置或上线。**业务主库＋原件存储**是两个存储主体，文本草稿和搜索索引按职责关联它们，不要求四套数据库或给每台员工电脑装主库。

| 数据 | 建议保存在哪里／如何关联 | 为什么这样分 |
| --- | --- | --- |
| 客户、订单／明细、反馈／正式结果、任务、权限、历史 | 一处关系型业务主库，按对象／版本／来源和明确字段关联；数量／单位／状态／金额性质等可供固定规则查询 | 精确统计与权限不靠AI解释自由文本；草稿与有效结果有不同状态和动作，不能互相覆盖 |
| 视频、图片、语音、文档／目录 | 服务端受控文件区或对象存储；主库留文件身份、不可变来源版本、存储定位、完整性、归属／引用和访问规则 | 大文件保留原件，不塞成大段文本；同字节／同名不合并业务权，上传与提取失败各自处理 |
| 可读正文、手工补记、提取／AI草稿 | 用文本字段及有结构约束的JSON／条件快照，留所指原件／版本／位置、处理条件和人工修正状态 | 人工路径可独立；AI整理不直接写正式结果，JSON格式本身不证明内容／资格正确 |
| 关键词／向量查询的派生索引 | 基于获准正文／记录及版本构建，可从相应来源重建；关键词与向量职责分开 | 向量不替原文／业务值，模型停用不应卡普通编号／名称／标签／已有可读文字查询；中文效果／性能和当前权限仍待产品验证 |

桌面和手机共用受控服务；客户端若有缓存／离线草稿，须显示未提交和来源时点，不成为另一套正式账。索引、图表和导出是派生，不能反过来决定正式进展或授权。数据库产品沿已有底座候选及兼容／维护条件选，不为向量检索先造两套业务主库；正文／草稿可与业务放同一数据库的不同对象中，物理方案尚未定。

例：上传获准截图→原图／版本保管、主库记身份及结果→识别正文／数量候选留来源→人工可查并核对→有权业务动作确认后生成某订单范围的正式结果。查单／统计引用该结果；原图访问另核，未知量不填0。没有AI时可直接人工补记本次变化，仍保留同样的来源、状态和确认边界。

备份／恢复要对应业务库、文件版本清单和必要配置／身份策略，另有受控备份位置及实际恢复核对；不只复制代码或某个数据库文件。恢复后核文件缺失／损坏、引用与当前授权，不盲复活旧访问权。正式数据及原件不放代码／GitHub仓库，具体存放在公司还是获准云地域、保留和恢复目标继续按维护方案定，不采购或初始化生产存储。

### 送货、收货与结算各留哪种关系

以下延伸完整B09／B10／B32及既有K5／T09／T10，不把它们塞成已批首节点，亦不重新决定完整会计、库存或开票建设。

| 概念／动作 | 需要关联什么 | 不能自动推出什么 |
| --- | --- | --- |
| 送货计划及明细分配 | 本次送货身份、原订单稳定明细／范围、计划量单位、目的地及版本 | 计划／打印不等实际发出；同规格不代同一行，跨单／多行分配先有依据 |
| 实际发出与物流反馈 | 本次实际货品／量、发生／登记时间、当前资格及依据；物流另记状态来源 | 工序量／计划量与已发不能相加；物流显示送达不代客户已核收货 |
| 客户收货反馈／有据收货 | 对应本次送货范围、客户所述和实际确认的区别、来源及差异 | 收到一部分不覆盖整单；无收货依据不填0或推定未收，资格／完成定义仍待核 |
| 少收／退回／补送／录错更正 | 对应原发出／收货范围，申请与实际事件、原因／替代关系 | 原事实不无声改写；退回申请不自动退款，补送不自动增加原需求或重复累计 |
| 账单／对账／发票资料 | 对方、期间、覆盖账项／业务、来源版本、整理／回复／差异和有据交接 | 订单价／发出量不自动立应收；对账、开票资料、发票发送与到账分开 |
| 到账线索／获准明细／分配 | 线索身份／付款方／所述值币种／实际时点及待核，已核账项与分配来源按适用规则关联 | 付款截图不证明到账；同金额／同客户不自动销单或分配，多款多单关系未核保留待处理 |
| 跨期／退款／冲回／收款跟进 | 实际发生、归属和登记分别留；引用原款／分配与申请／实际结果 | 不挪日期凑统计，不见负数就抵款；无到期依据不判逾期，普通任务期限不代款项到期 |

每种数量／金额保留性质、范围、单位／币种、版本和来源，适用规则明确才汇总；部分记录不能冒充完整基线。角色、确认／更正、账期及匹配等真实未知继续内部留档，不新增用户问题。相关页面见[P06／P07完整草图](../页面与原型/基础版关键页面草图.html#p06)，未来对照见[分批验收T09／T10](../施工与验收/基础版分批开发与验收表.md)。没有业务表／接口／存储部署或财务执行。

| 登记客户接受／W06 | 哪一版、哪些明细和交易条件、接受范围／原文与来源 | 内部通过不代客户接受；“收到”或含糊回复不自动接受全部；部分明确的先记录，不擅把整份报价成立为订单 |
| 建立／查回订单及交接／W07/W14 | 已核的成立条件、可靠接受范围与当前资格、一次操作身份 | 生成或查回对应订单／明细及来源版；重复／回执未明查原操作。群通知、内部／供应商下单、PMC安排各留依据，不推定已执行或开工 |

上述是六类业务含义，不要求六张独立表／六个系统／六轮点击。报价、合同、订单实际身份及一对多／合并关系尚待依据，当前先保留稳定引用与接受范围，不照旧列表名字强定物理模型；系统也不从客户称呼猜账号或正式确认权。

变更后以受影响内容和范围决定哪些审核／接受需重办，保留原版有效性及历史；不全盘继承旧批准，也不规定所有轻微修订一律找老板。已建立订单的后续要求变更走现有受控变更，不因新报价草稿直接覆盖当前订单。

本轮只将已有主管图、报价版本摘要及S-A收拢到动作／页面，没有核公司新规则、生成对外正式报价或操作生产。G01／02／03等按原影响保留，用户暂缺项集中在总表，当前不新增提问。既有数值承载／入口研究在后续章节，不在本轮重开技术选型。

## 1. 让普通功能自己工作

人提交内容→系统按当前权限保存草稿或办理明确动作→固定规则处理合法输入→保存本次依据和结果→普通列表／详情／固定统计显示同一结果。AI不是必经步骤，也不负责判断某人是否有确认权。

同一份资料的原文、提取候选、人工核对和正式业务结果分别有身份及来源关系。原件不改写；正式结果不以“最新上传文件”或相似名称自动替换。这里只规定职责和关联，不要求为每个阶段再部署一套服务／数据库。

## 2. 哪些信息属于哪一处

名称是业务概念，最终字段与物理存储仍按所选路线定；有依据的已知项可留，缺项不补猜。草稿必需条件与正式办理必需条件分别定义，不把所有字段一律必填。

| 概念／对应任务 | 必须能够表达的内容 | 用途与限制 |
| --- | --- | --- |
| 客户／联系人／需求／W03 | 稳定客户身份或未核对象、适用联系人及归属、客户原要求／来源、材质形状尺寸数量等已知内容／缺项 | 联系人不等账号；未知客户不自动合并；需补信息可停在草稿 |
| 报价身份／内容版本／W04—06 | 报价及明细身份、本次版本、客户本次模式／依据、采用的条件来源、不同动作的结果关系 | 净尺寸优先由用户说明；本次实际方式仍承接客户要求，当前偏好不重写历史（候选设计） |
| 尺寸／数量／单位／W04—05 | 原始表达、已核数值或缺项、单位、用途；净尺寸、报价计重、采购下料／加工余量各自含义 | 同一个“长宽厚”不能代所有用途；件数／重量、单件／总量分开，不用显示精度改原值 |
| 单价／费用及适用条件／W04—05 | 成本或售价用途、币种／计费单位、本次有效值／来源、费用适用性及单件／总量基数 | 不适用与未知分开；不把内部成本自动外发。人工价格按适用资格／规则处理，不用手填绕过条件 |
| 规则／精度／计算解释／W04—05 | 规则身份／版本及适用条件、必要的有效时间、计算中间值用途、精度／舍入点、输入与输出关系／缺项 | 重量舍入方式用户已回复“待核验”，不默认平台两位或公司统一HALF_UP；本例Decimal只作参考 |
| 审核／外发／客户接受／W06 | 操作者及动作依据、对应内容版本、适用决定／发送对象与结果、接受内容及来源 | 内部通过不代客户接受；预览不代已发；改版是否重审按适用规则，不统一新增老板审批 |
| 订单／当前要求／范围基线／W07 | 新单或在途接续来源、稳定单／明细及适用范围、当前要求及已知基线／缺口 | 接续不强补旧报价，不算新成交，基线未知不从0算累计／剩余 |
| 反馈／有效进展／纠正关系／W08—09 | 本次内容／时间／来源及范围数量含义、核对与业务确认分别有据、原结果／更正原因／替代关系 | 当前局部4更正3不加7；返工／真实追加与录错更正分开，部分结果不代表全单或合格 |
| 独立事项／逐人事件／W10 | 事项身份、草稿／发布要求与接收范围版本、已生效责任／期限及待变化、回复／决定／验收依据和逐人所指内容版 | 可无订单／非必需附件；事项身份持续，当前责任不覆盖旧发布／回复署名；草稿、发布、发送、送达、阅读、回复、执行／验收不强并完成，无阅读依据不硬判未读 |
| 原件／版本／引用／W11 | 稳定文件及不可变来源版本、逐件状态／指纹／存储定位、人工标签、独立保管或可靠引用、适用读取权 | 文件身份→不可变版本、清单→逐项条目分开，成功才指实际保存版；注记不盖字节；同名／同内容不合并业务权，关联可见不代整件权 |
| 一次办理／结果回查／W14 | 操作身份、当前操作者／对象／动作／输入关系、所见版本、实际结果及关联新版本 | 客户端角色不作授权事实；重复要能认同一次，超时后查原操作，不根据新偏好重算原结果 |

原始表达和来源可按具体字段或条件快照组织，不强制每个普通数值加五列或存五份。正式业务保留一处权威值；显示／索引／统计投影是有版本关系的派生结果，不形成两套可各自改写的主数据。

## 3. 数值承载有三种候选，当前不偷选

| 做法 | 可借的基础／要做的工作 | 在决定前必须检查 |
| --- | --- | --- |
| A1用原生Currency／Float等字段 | 框架录入／查询／显示省通用建设，但已见驱动／文档及JS转换 | 保留原输入与实际规则；在公司所需范围／精度下完成计算、保存读回、再计算、汇总与真实输出对照。不因存在float就直接判全部错误，也不因decimal列就判通过 |
| A1显式保存精确条件／结果，并派生展示 | 可考虑规范十进制文本／明确数值与scale承载关键输入／结果，按本次版本用固定计算；原生显示字段只承接投影 | 实际字段、长度／范围、查询汇总、索引、版本一致、权限和迁移成本；不能把文本与数值都当可随意改的正式值。不是已经采用字符串金额或每个字段用整数分 |
| C按业务服务＋Decimal／numeric设计 | 用成熟DB／ORM等组合，按业务定精度、列与API表达 | ORM／驱动／JSON／前端／报表仍要核，不能仅选PG便宣称精确；同样处理scale、溢出、有限性和逐步舍入 |

先比较满足业务精度及解释／历史／查询成本的最简单方案。不能为修一个转换就未经验证全局替换平台decoder；也不先另造一个正式计价库再和平台双写。选型有差异时保持本稿业务概念和验证答案不变，换实现方式即可。

三者关系必须清楚：原始表达保留来源，规范值按本内容版的单位／scale及精度／规则解释，显示是可追溯的派生。若选整数，不能只存整数再用当前全局scale解释旧报价；若选文本，数值比较／排序／聚合须采用受控解析及范围规则，不用字符串排序冒充金额排序；原生Currency若作投影也不能另行成为第二权威值。这些是候选采用条件，尚未选定物理字段或统一整数分。

## 4. 草稿可以留原话，正式数值不能猜

| 输入情况 | 草稿／资料接收建议 | 计算及正式动作建议 |
| --- | --- | --- |
| 必需值未知／单位或模式未明 | 有权且有可保存内容时保留原文／缺项，不逼填0 | 不能形成正式价，给具体待核原因 |
| 原文含非法数、歧义分隔符或解析失败 | 原文可作为资料／草稿线索保管；规范数值不伪装成功 | 拒绝把无效值当0或有效报价；不把“已保存资料”当“已算好金额” |
| 明确为合法0 | 按该字段／动作的适用规则保存0及用途 | 不与未知混同；不是所有重量／价格／费用都当然允许0 |
| 明确不适用的费用 | 标不适用及依据，可不制造无意义数字 | 按该计价规则处理，不强行成为缺项或推定免费 |
| NaN／无穷、超范围或超出允许精度 | 可保留来源及拒绝原因 | 拒绝无声截断／溢出／非有限值进入正式计算；超精度是否允许舍入按明确规则 |
| 原规则／条件变化 | 新的待处理内容与原版本分开留 | 不回写旧报价或继承全部旧批准；是否生效／重审按适用规则 |

JSON采用字符串可保留十进制表达，但仍要明确schema、合法格式、单位／范围及服务端解析；不存在“只要是JSON格式就可信”。正负数样例只是数值机制检查，业务动作是否允许负数另定。

## 5. 关键动作由服务端办理

以下是语义契约，尚无正式路径／代码。身份从当前可信会话取得，客户传来的岗位／操作者名称不作授权依据；数据当前版本和规则引用也要由服务核实。

| 动作 | 服务端应核的内容 | 结果边界 |
| --- | --- | --- |
| 保存需求／报价草稿 | 当前编辑权、允许字段及所见版本；如提供关联则核可靠性，未核客户／对象可保留独立草稿；核原文／缺项可留的范围 | 可查草稿或具体拒绝／冲突，正式推进前明确必需关联，不额外产生审核／接受／订单 |
| 计算本版报价 | 本次模式／规则、合法输入／单位／费用及精度；当前计算资格 | 本版解释结果或待核／错误；不能顺便外发、批准或下单 |
| 适用审核／外发／记录接受 | 对应内容版本、该动作权和适用条件／依据 | 各自结果分别有据；异步排队不当已经完成动作 |
| 建新单／接续在途 | 新单可靠成立内容；接续当前对象／范围／基线及缺口 | 当前来源清楚，不伪造历史，不扩大现有进展 |
| 确认反馈／更正进展 | 当前范围／动作权、所见版本和来源；原结果／更正原因按动作适用：初次确认不强求既有结果，录错更正才必须明确被改结果及依据；核对和正式动作分开 | 有效结果／适用替代关系或拒绝／冲突，不能靠通用字段更新跳过；后来返工另留事件 |
| 普通事项及回执 | 发布／回复／验收各自适用权和原事项；逐人状态有实际依据 | 无订单可办；A回执不代B，也不代表业务验收 |
| 查询／输出／文件读取 | 当前对象／字段／整件／动作范围，实际请求人与适用时点 | 只给获准内容，后续生成／领取／重开也要核；不靠旧服务账号权放行 |

资源CRUD、单字段更新、文档保存／提交、白名单方法和后台程序都要列入入口清单，关键字段不得从任何未获准路径直接变成正式结果。平台有校验机制可以复用，但直接数据库更新可能跳过控制器；调用者必须通过统一业务办理或承担等价可核规则。服务内部的“允许本次动作”不能作为客户端可随意传入的开关。

后续Agent读取也核实际请求人，而不只核平台服务账号：进入重排／模型前及引用重开时核当前片段／字段／版本与外送范围，混合成本原件不先全送后遮答案，撤权或核权不可用不沿用旧上下文。它仍属于后续增强，关闭Agent不阻断获准人工路径。

## 6. 一次办理、版本和通知怎样接上

建议把原操作身份和业务版本分开：前者回答“是不是同一次提交”，后者回答“是依据哪一版内容办理”。操作身份不单独赋予权限，也不代业务对象身份。

操作键的命名范围／绑定由服务按可信主体、动作、目标及规范化输入／所见版本核实。同主体／动作／对象／内容的原操作重试才按既定重放规则处理；其他账号猜中键不取得缓存内容或原操作存在信息，即使可看该业务对象也不自动成为原办理者。交接／代办须另有适用授权，查询原操作同样核当前权。当前权／所见版本核验与正式写入要有可核的原子性边界，不能先独立查版本后无条件写。

先核本次入口及返回内容所需的当前身份／权限，再按主体／动作／目标／原输入及所见版等绑定识别原操作；有据已成功的同一原内容合法重试，只在获准回查范围解释当时结果，不再执行业务写入，不因原请求携旧版就迫其换键重做。原操作当时结果和当前有效结果各有含义，旧回执不能反写当前。确属未处理的新写入才按其所见版本核新写冲突；结果未确定仍保留未明，不因一次未查到就当未执行。变内容／对象／原所见版不是原内容重放；当前无权时受控拒绝亦不否认过去可能成功。

| 情况 | 候选处理与应检查结果 |
| --- | --- |
| 首次办理 | 当前权／内容／版本校验满足时，正式记录与可回查办理结果在适用事务中一致保存；文件字节另有逐件状态，不假装同一DB事务 |
| 相同操作重试、内容一致 | 原主体／动作／对象／输入和所见版绑定一致且有据已成功时，按本次当前可见范围查回当时结果、说明当前适用版；不因原携旧版重走写入，不重复确认／建单／通知意图。仍未明就核原状态，不当没执行 |
| 相同操作身份却换内容／对象／版本 | 标冲突，不以重复名义静默改办另一件事 |
| 未处理的新写入所见版已旧或应带却未带 | 依据具体动作拒绝／要求重查，不让通用更新自动拿服务端新版本代替客户原编辑依据 |
| 保存成功但回复未获 | 查原操作，不盲换身份重发；未查到结果也不直接证明未执行 |
| 通知尚未送达或重复投递 | 业务保存与通知状态分开；待投递／重试对应原事项及接收者，不再建新业务结果、不伪造已读 |
| 后来撤权／调岗、旧结果重开 | 重新核当前可见／动作权；不能因旧操作曾有权就再次暴露整件或重新执行 |

同操作防重不代同业务事实防重：换了操作身份仍可能重复同一笔建单／反馈，适用业务身份及重复条件要另定；也不能仅凭相同文字／数量吞掉确实发生的第二次业务。通知业务意图／接收者事件不重复创建，不等外部物理消息恰好投递一次；投递可以重试，须按原事件和逐人状态核对，不伪造已读。

这是W14设计要求，不表示平台已提供完整实现。现有修改时间校验、合成PG确认／更正与文件恢复实验仅在各自条件下参考，不能充当本稿跨对象／并发／故障与目标环境通过证据。具体事务、唯一约束、锁／版本与异步投递方案仍要按所选路线检验，不能单靠一个按钮禁用或一条前端UUID。
