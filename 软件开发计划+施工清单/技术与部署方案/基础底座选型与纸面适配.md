# 基础底座选型与纸面适配

2026-10-27；revision 6；supersedes r5：回填首节点HTTP小链有限运行与退出证据，原比较和规格保留；前稿项目外保全。proposed／候选规划，非正式开发或产品验收。


## 1. 现在推荐怎样安排

**先审谁承接维护、首批目标和投入量级，再比较Frappe框架＋隆实独立应用与成熟组件组合，不默认自维护Frappe优先。** 用户已答维护方尚未确定；不能默认实习生或AI兜底，亦不能据未验证的旧客户端语言／形态判断候选必然更重。[投入／职责／卡点说明](../决策与变更/2026-10-27-首批投入量级与维护安排.md)优先于此前的调查排序。 复用成熟表单／权限／流程基础，但公司报价、订单接续和确认／更正由明确业务规则控制。ERPNext现成业务只在能自然映射时复用，不能强迫员工补造历史；Odoo保留对照，NocoBase暂降备选，理由和原始来源见调查稿。

所有路线都先做好无AI也能登记、办理、查询、固定统计与输出的系统。后续Agent通过受控查询及草稿交互增强，不获得正式业务写入入口。既有完整36组功能保留，当前只收敛首批候选的施工方式。

图是逻辑分工，不要求六套微服务。A1由Frappe和隆实应用承接；C由一套业务服务及按需组件承接。文件处理、索引和统计可有独立任务，但不成为第二套正式事实。AI不在人工核心办理的必经路径上。

数据库分支：A1先核固定版本下目标数据库与自建应用／所需扩展的完整兼容性；A2以现成应用已支持组合为前提，不能从框架文档推定应用可用。C优先核PostgreSQL及既有有限证据，框架FastAPI／Django／.NET等不因技术建议就自动锁定。后续语义检索如另有索引库，必须明确一向可重建、当前权限和时点，不用双写两个主库解决选型矛盾。

## 4. 人的办理入口与数据交接

这里是语义接口候选，不承诺某个上游端点已经满足。具体路径、请求／响应字段和错误码在路线收敛后补，不提前堆完整API。

| 人的动作／任务 | 输入和交接 | 结果与继续条件 |
| --- | --- | --- |
| 保存客户／需求草稿／W03 | 当前账号；已知字段／来源；更新时带所见业务版本 | 可查草稿与缺项；不能因保存成功就认为可正式报价 |
| 计算／保存本版报价／W04—05 | 实际模式、有效规则版本、尺寸／单位／数量及适用费用；服务器重新核输入和动作权 | 固定计算解释或缺项／冲突／待核；尚未确定G01时不产生正式可外发价 |
| 审核、外发、记录客户接受／W06 | 各自操作者／适用资格、对应内容版本及依据 | 分别保存结果；不能只靠改同一个status完成全部动作 |
| 建新单或接续在途／W07 | 新单可靠确认来源；接续可靠当前对象／范围／基线及缺口 | 有依据的新单／接续记录或待核；不伪造历史流程 |
| 反馈、业务确认、变更或纠正／W08—09 | 指定范围／数量性质／时间、证据和原结果版本；各动作当前权 | 反馈与有效进展分别显示；录错纠正与真实追加分别保存 |
| 发布独立事项／回复／验收／W10 | 事项、负责人、实际接收范围、期限及适用依据 | 各自可回查结果和逐人状态；是否需审批按事项类型定，不统一老板审批 |
| 保存／引用／读取文件／W11 | 逐件身份／完整性状态／版本；可独立标签保管；关联必须可靠 | 逐件结果；读取与下载核当前整件权，原件／预览／提取结果各有来源 |
| 普通查询／固定统计／输出／W12—13 | 当前账号、固定查询主题、过滤／期间／状态／单位与数据时点 | 只返回获准行列及说明；产物生成和领取都要核权 |

W14贯穿：需要重试的写入保留同一次办理身份；更新引用所见版本；保存后回执未明先查原操作结果。成功、拒绝、冲突、仍未确定各有明确表现，不能自动换一个操作身份反复提交。是否采用平台现成事务／版本机制，需按相同反例检查，不能仅凭官方有save就放行。

**平台自动CRUD／RPC入口也在授权范围内。** 关键动作不能只在新页面校验，而让通用更新接口直接改成“已确认”。Frappe官方提供DocType CRUD和白名单方法；Odoo官方也提醒公共方法参数不可盲信，均需核服务端实际入口。后续Agent采用受限的查询／草稿能力白名单，不直接拿普通员工写凭据、数据库管理凭据或通用写接口；“界面只放查询按钮”不能证明AI只有读权。依据见[路线调查来源](../../AI调研/技术调研/2026-10-27-基础系统实现路线比较与验证门槛.md)。

本轮另读Frappe v16.53.0 `_save`／`check_if_latest`／`run_before_save_methods`与handler方法分派的相关部分，已有写权／修改时间／保存前钩子等可复用机制，故可以把规则放在服务端；仍需明确通用更新、专用业务动作及后台路径如何一致生效，不把只读源码当全链运行证据。`ignore_permissions`等服务端机制不是自动存在的客户端漏洞，也不能在扩展中随意用来跳过公司授权。数字字段持久化／舍入与跨对象保存结果仍待验证。

后续指定源码补查已形成[计价精度与业务入口核查](../../AI调研/技术调研/2026-10-27-计价精度与业务入口源码核查.md)：两数据库适配器的十进制列／读回float、文档数值转换、前端显示／舍入、资源更新／单字段／界面保存、db_set、文件权继承和报表导出指定路径。数据库类型与显示精度不能证明全程Decimal；只在保存控制器加规则也不等所有写入口覆盖。需先保留原始数值／单位／验证状态，按有效规则计算，检查字段／驱动／JSON／界面／产物往返；不未经兼容验证全局改驱动。db_set有不触发控制器验证的说明，正式动作不得由后台直接改字段绕过。文件private也不自动表达“可见进度但不可读整件成本附件”，自身权限／引用方式须适配。均为机制／约束证据，不是已复现平台漏洞或公司场景失败。

Agent的服务账号读权不替代请求人权限；检索片段进入重排／模型和引用回看前，核当前范围／字段及外送许可。混合敏感整件不先全送再遮答案，核权失败不沿用旧上下文。以上是未来接口约束，不让AI成为本批人工办理依赖。

## 7. 准备度核对后的第一项窄验证（规格保留，有限执行见第8节）

选定发行／应用／数据库组合，能否在不靠AI、不放宽权限、不补假基线的情况下，把同一笔更正可靠保存、查回、引用到清单并生成可核产物？这比再加候选组件更能校准适配／维护代价。
