## 员工应该感受到什么

上传中断后，先查系统有没有收完，能续传就接着传，避免重传整段视频。原件收好后，即使AI没识别完，也能明确看到“资料已保存，待整理”。同名文件不覆盖旧资料，改了新版仍能追到旧版；文件夹只传成功一部分，就逐项说明，不假称全夹已保存。

保存资料、提取、核对、按类别上报、正式业务确认分别处理。识别失败不删原件，上传成功也不自动算上报完成、订单完成或审批通过。

## 1. 分清需要记住的几种身份

下面是职责和关联，不是已定数据库表名或正式API。

| 身份/记录 | 保存什么，解决什么问题 |
| --- | --- |
| 一次提交与上传会话 | 操作身份、请求摘要、当前授权范围、每件上传进度；回复丢失时可查询原操作，不用新标识盲目重试 |
| 文件及不可变版本 | 原字节、受控存储定位、大小/内容指纹、显示名/类型、来源及上传时间；改名/移动不改变已保存字节版本 |
| 文件夹清单版本 | 原相对路径、空目录、逐项文件版本及结果；显示目录与内部存储键分开，不能直接用任意路径写服务端目录 |
| 资料归属与业务引用 | 谁提交、与哪些获准对象关联、所指文件/清单版本；同字节不自动成为同一次业务或共享全部权限 |
| 提取运行、文本与草稿 | 输入版本、工具/配置版本、尝试与输出；原始提取、人工修正及核对保留，重提取不覆盖旧确认 |
| 恢复集合及核对记录 | 数据库一致备份、实际被引用文件版本清单、配置和必要人工/审计记录的对应关系；恢复时逐项核，不只看“备份成功” |

“最近上传的文件”“名字一样的文件”“业务上当前有效的版本”不是同一个概念。最新上传不能自动取代已确认订单依据；并发更换当前版本时要核期望版本，冲突交有权者处理，旧版保留。

## 2. 上传的完成点与员工提示

```mermaid
flowchart LR
    A[有权创建提交和上传身份] --> B[分件上传暂存字节]
    B --> C[服务核实际接收量与内容校验]
    C --> D[登记不可变版本和引用]
    D --> E[原件已保存]
    E --> F[按需排队识别或人工整理]
    F --> G[候选 核对与类别上报]
```

| 情况 | 系统应怎样处理（待验证） | 员工端可见提示 |
| --- | --- | --- |
| 上传中断 | 核当前身份/同会话与已收偏移后续传；会话过期/原内容已变须明确重建，不盲接旧字节 | “上传中断，正在核对进度” |
| 客户端没有收到完成回复 | 查原提交的服务端结果；已保存则复用该结果，未确定前不换操作标识重发 | “正在核对是否已保存” |
| 字节收全但校验未完 | 只报接收/校验中；实际大小/内容不符不发布可用版本 | “已接收，正在校验” |
| 文件已有而数据库登记失败 | 保持受控暂存/待核，不假报资料已保存；恢复登记或核引用后清理，不能失败就随意删原件 | “保存结果待核，请稍后查看” |
| 数据库有记录但文件暂不可读 | 标原件暂不可用、阻止把缺文件当可处理；恢复后核指定版本，不偷换同名文件 | “原件暂不可用，正在核查” |
| 原件保存后识别失败/排队 | 原件保留可按权限查看；记录独立提取状态，可按原版本重试或人工整理 | “资料已保存，识别失败／待处理” |
| 文件夹部分失败或回执不明 | 返回每项状态和空目录清单；结果未明项先查原操作/会话，只对核实未完成且当前有权的项续传/重试；不盲目重交整夹 | “部分已保存，部分结果待核，请查看逐项状态” |
| 文件夹选择清单尚未枚举完 | 清单自身保留未完成状态；当前看见的项数不是完整总量，无法读取的条目也保留具体失败；不按已传项数报整夹100% | “正在整理本次选择的文件清单” |
| 取消与完成相遇 | 取消请求与取消已生效分开；已经保存就明示，不能显示取消却暗中新增结果。取消提取不自动撤销原件或正式事实 | “正在取消”或“已保存，未取消该版本” |

原字节校验与能否解析是两项检查：未知格式、加密或暂不可读的原件，按获准保管范围分别记录；不能凭解析器失败宣布源文件为空/损坏，也不能把“已收全”当内容可处理或业务正确。分片校验是否足够、整件校验方式及各协议完成语义按候选实测确定。

传输资源字节收齐、不可变原件版本及目录登记完成，分别有可核对的状态/回执；tus的HEAD偏移与PATCH成功本身不代表本系统保管事务完成。若采用[tus 1.0.0协议](https://tus.io/protocols/resumable-upload.html)，续传先查服务偏移；偏移不符按协议拒绝并重新对齐，不靠本地已发量推断。创建POST本身不提供本系统业务防重，可选终止/过期/校验扩展也须核所用服务实际支持。

停止客户端、终止传输、取消后台处理、删除已保存原件分别授权和执行。固定[tusd 2.10.1 hooks源码](https://github.com/tus/tusd/blob/v2.10.1/pkg/handler/hooks.go#L7-L19)说明请求context取消后仍可有尾部字节处理；本次只核机制，未跑取消竞态。旧状态外显带时点或“尚未刷新”，接收/保存/处理/业务发生时间分开，不把上传时点充业务发生时点。

重复操作的标识须绑定请求内容和主体/范围；相同标识但不同内容拒绝。查看原操作也核当前权限。文件内容指纹只用于字节完整性及受控存储去重，不自动合并业务记录，不向员工泄露“其他部门也上传了同一文件”。

## 3. 新版、重复与后台处理

| 变化 | 保留的边界（待验证） |
| --- | --- |
| 两人上传相同文件名、不同字节 | 分别保留身份/归属和字节版本，不能按名称覆盖；是否关联同一资料由可靠上下文和有权核对决定 |
| 相同字节用于不同订单或权限 | 可另评估底层字节复用，但逻辑提交/业务引用/权限仍分开，删除一份不得损坏另一份仍有效引用 |
| 同一资料新版本 | 建新字节版本、保留旧引用；“当前展示版本”和正式业务所引版本分开，不能批量改写过去证据 |
| 旧提取任务晚到 | 输出仍归原输入版本；新核对/新版本不被覆盖；发布时核当前任务、版本和处理/读取授权 |
| 改名/移动目录 | 变显示清单/关系，不改原字节身份；保留原相对路径，大小写/字符归一化冲突须可解释，不静默丢条目 |
| 删除/作废/交接 | 先按公司尚待明确的规则决定可见性、历史引用和审计；物理清理及备份保留另定，不擅设保留天数或自动永久删除 |

用户在2号曾提出共享文本云端主版本、大素材云存储、客户端按需副本/可清缓存及安装包不带完整库，且要求先看分析；1号已回读原人类消息，不只引用代理摘要。本段按该设想优先分析：清本地副本不等于删共享原件，安装包不携带全量公司业务库，按当前权获取版本。具体云服务/资料地域、离线允许读什么、缓存何时失效和交接规则仍待明确，不因有副本而开放失效授权，也不把此设想当采购或生产数据外送批准。

## 4. 坏了以后，怎样才算找回来

候选恢复顺序为：**隔离恢复 → 核数据库及被引用原件清单 → 核人工修正/历史引用 → 对齐当前身份与权限 → 对账未完任务 → 重建必要索引 → 复核后开放对应能力。** 每步失败只报告恢复到哪一步，不把“文件复制回来了”当全系统恢复成功。

1. 数据库使用其支持的一致备份机制；普通在线复制数据目录不能视为可靠数据库备份。[PostgreSQL 18文件系统备份文档](https://www.postgresql.org/docs/18/backup-file.html)说明停机复制及一致快照等不同条件，不意味着数据库一律必须停机才能备份。
2. 数据库恢复点中的每个原件引用，须在恢复集合内找到对应版本并核大小/内容指纹。数据库备份与文件备份完成时间相近，不足以证明引用闭合；并发上传、版本切换及清理期间怎样形成闭合清单仍须设计和验证。
3. 人工修改过的文本、核对记录、业务历史及证据关联不能只靠重新OCR补回。派生索引可重建，但在源/权限未对齐前不开放旧索引。
4. 恢复旧权限副本不等于恢复当前合法访问。离职/撤权/交接须与确定的当前授权依据对账；无法确定时保持受控，不自动重新放开资料。
5. 旧队列/待办不可恢复后直接全部重放。先停外发与业务副作用，分清已成功、不确定和可重试；提取也要重核输入版本、当前授权和资源预算。
6. 备份工具写出快照、仓库结构检查、逐文件恢复校验与业务可用验收分别记录。[restic备份文档](https://restic.readthedocs.io/en/stable/040_backup.html)提供快照/检查机制，但不能替数据库一致性、应用引用和权限对账。[恢复文档](https://restic.readthedocs.io/en/stable/050_restore.html)另说明原地恢复的中断/覆盖风险；本契约优先隔离目标恢复核验，不把工具默认覆盖行为当业务替换规则。备份访问与必要密钥另行受控保管，具体责任人未定。

## 5. 存储路线怎样继续比较

| 候选路线 | 适用思路及保留职责 | 当前限制 |
| --- | --- | --- |
| 业务服务控制的文件目录＋元数据 | 可作为较简单的验证基线；员工经业务接口访问，文件字节与逻辑目录/版本分开 | 不能让员工直写共享目录；配额、并发完成、目录清单及跨备份一致恢复由应用设计和验证，未决定采用 |
| SeaweedFS等自托管对象接口＋元数据 | 若容量、大文件及接口条件需要，再核具体对象/版本能力及运维代价；除业务元数据外，具体路线可能还有volume、filer及其store等恢复依赖 | 已有安装者的master健康基础检查不代表S3版本、复制、耐久或恢复通过；不直接套用所有AWS语义 |
| 获准的受管对象存储＋元数据 | 若公司允许资料位置、成本和维护方式，可比较存储/版本/权限及恢复服务 | 具体供应商、地域、费用、网络和资料许可未定；服务端版本/复制不自动等于独立备份 |

数据库/文件/身份/任务的职责不随存储品牌消失。本轮先细化契约和失败场景，不启动组件，也不凭已有安装锁定生产选型。
