## 1. 当前阶段与已确认方向

- 目标是公司内部使用的Windows桌面管理软件，交付形态包括可安装程序。
- 当前先利用已提供资料，形成大致业务、模块关系和页面概览；继续调研安排，精细历史事件不阻塞概览。
- 业务经理九个问题仍在等待回答，由用户收到回复后统一提供。当前不催问、不追加，也不从模型或旧资料猜测经理的回答。
- 公司仍使用USteel。已取得的界面显示澳新ERP管理系统v1.0正式版，客户端版本为1.2.16.52。数据库类型、接口、授权方式及可导出范围尚未确认。
- 用户报告大量客户端导出存在缓慢或卡顿，助手没有复现或定位原因。当前不安排反复大批界面导出；未来确需取数时再按用途申请授权，比较受控副本、厂商只读服务等路线。
- 正式业务开发、生产系统访问和取数没有因本摘要的发布而获得授权。需要公开提交的工作由协调窗口统一核查和执行。

## 2. 已理解的业务对象与联系

业务围绕模具钢材及配套加工开展。主要联系包括：

**渠道获客或业务开发 → 客户跟进与需求确认 → 材料、模胚或外协报价 → 客户确认及下单 → 采购、入库与生产计划 → 内部加工或外协 → 检验及交付 → 对账、回款和成本利润分析。**

未成交复盘、质量异常和补料可能返回前序处理；实际先后和是否经过全部环节需按业务核实。日常汇报、行政报销、点检、任务与通知等有独立场景，不强行全部挂到订单上。

| 对象类别 | 已整理的字段类别 | 需要保留的区别 |
|---|---|---|
| 客户、联系人、供应商 | 主体标识、名称别名、来源渠道、业务归属、适用结算信息 | 同名不等于同一主体，名称不替代稳定标识 |
| 员工、部门、岗位 | 账号与业务代码映射、部门、角色、归属及交接 | 姓名不等于账号，兼岗不等于可看全部资料 |
| 询盘、报价及明细 | 需求、材质规格、数量、单位、报价与成交情况、时间 | 询盘、报价、成交和收入是不同概念；一行未必是一单 |
| 订单、加工与外协 | 对应业务标识、要求、供应商、计划和实际进度 | 客户模号、内部编号、订单号、加工单号和外发单号分别识别 |
| 检验与交付 | 规格、公差、检测项目、实测、交付数量与凭证 | 有模板或报告不等于已检验合格、已出货或已签收 |
| 对账、收付款、费用与利润 | 原始、调整与确认状态，费用类别、业务期间和凭证关系 | 对账与到账分开；客户期间汇总不是单笔回款 |
| 异常与补料 | 关联业务、原因、规格数量、责任、费用及处理结果 | 相同字段不自动证明重复，责任认定不由AI推断 |
| 原件及派生资料 | 文件类型、版本、出处、提取与核对状态 | 原件、扫描回传、文字提取、汇总和正式事实分层保留 |

## 3. 新系统要支持的管理能力

员工提交文字、图片、语音、视频、表格等资料；系统保留原件并帮助整理、查找。主管和老板按权限查看，老板通过看板及有依据的问答掌握全局。

工作协同需求已明确：老板下发任务、发布通知、处理适用审批，员工能够反馈。围绕事项的留言、进度、附件、提醒和状态是待审设计；独立即时聊天、多级及代理审批等仍待核实。

默认范围为员工查看自己提交的资料、主管本部门、老板全公司。必要协作与交接例外另行明确；接收一项任务不自动获得关联成本或利润的查看权。权限需一致覆盖列表、原件、搜索、AI和导出。

AI可在授权范围帮助提取、检索、总结和生成草稿；不得自行修改正式业务事实、批准事项或发布正式任务。正式确认及写入由授权人员和业务系统负责。

## 4. 首工作段实际观察到的情况

以下只保留研究结论，不包含真实主体、业务标识、数值、原件路径或指纹。

| 样本类别 | 已完成的有限观察 | 尚不能证明什么 |
|---|---|---|
| 普通业务路径候选 | 定位到检验记录及客户级台账线索，比较文件和局部区域，发现副本及实测空白 | 未贯通同一业务的报价、下单、交付、回款，不称为已正常履约完成的订单 |
| 对账调整异常 | 以相同送货标识及一致明细，关联工作簿、原对账文件和扫描回传；回传存在负调整，客户级汇总有同方向记录 | 不证明文件生成时间顺序、正式调整授权、业务生效、银行到账或核销 |
| 工作簿内部冲突 | 同一文件的公式及保存缓存与硬编码金额文本存在不一致 | 未运行Office重算、核对实际打印区域或确定哪个数值已正式生效 |
| 补料及历史记录 | 发现相似内容而责任归属不同的条目，亦发现与其他期间记录不能直接连接 | 不能按同客户、日期、规格或金额自动删除记录或拼成同一异常 |
| 日期与字典 | 目录、标题、行级日期可能不同，业务分类存在不同维度 | 不以文件夹决定业务时间，不擅自合并不同含义的分类 |
| 文件读取边界 | 部分扫描文件没有可选文本；部分标称格式与实际容器不符 | 空文本不等于空文件；未读出不等于损坏，不擅自改后缀或解密 |

## 6. 对后续设计的研究结论

下列为proposed设计约束，供后续审阅，不是已定技术栈：

1. 分清客户、订单、订单明细、加工、送货、对账及收款的粒度；不能仅凭同客户同日同金额配成同单。
2. 正式业务记录、待核草稿、原件、可搜索文本和汇总分别保存职责；查询和统计不能把同一事件的多种表示重复累计。
3. 字节副本识别、模板局部比较与业务事件去重是不同问题；扫描回传可能是有差异的相关版本。
4. 分开原始值、调整值和正式确认值；冲突先呈现并保留出处，不由AI静默选择并覆盖。
5. 报价、成交、计划、实际完成、交付、付款、上传和提取时间分别表达；未知或空白不自动当零或成功。
6. 对账调整、检测和付款状态以对应业务确认依据为准；文件名、可见章或提取文字不直接决定状态。
7. 与USteel的共存或未来替换按对象明确主版本；暂不预定全部重建或永不替换，也不假定接口已经存在。
8. 图表和AI回答保留口径、时间及来源回溯；无事实或规则时说明缺口，模型总结不反向改写事实。
