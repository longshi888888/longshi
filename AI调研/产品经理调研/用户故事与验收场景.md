# 产品经理调研｜用户故事与验收场景

状态：验收建议草案；以下均不是已经实现或测试通过的功能，尚未确认的业务规则需补齐后才能转为正式验收。

需求编号见[功能优先级与范围建议](功能优先级与范围建议.md)。尚未制作可视原型，流程关系参考[数据流与关联设计草案](../技术调研/数据流与关联设计草案.md)。这些故事保留各自可验收的结果，同时明确依赖，不因通用模板要求“独立”就声称它们可任意顺序开发。

## PM-US-01 员工提交资料，并知道处理到哪一步

对应：PM-REQ-01、07、08。

作为员工，我希望把权限内的业务资料提交给系统，并能看到原件及处理状态，以便知道是否需要补充或重试。

讨论：具体首批类型、文件大小、文件夹规则和上传归属方式仍待核实；不能把本故事当成已经决定所有输入类型的交付批次。

验收建议：

1. 采用已确定支持的类型提交后，能看到对应原件、提交身份、时间和稳定的资料标识。
2. 能区分接收完成、处理中、处理失败及需要人员处理的情况；不能以“上传成功”暗示内容已经确认。
3. 归属已指定时核验访问权；归属不明时按最终确认的处理规则表达，不擅自挂到相似客户。
4. 不支持、损坏或中断的资料有明确结果；重试不造成无提示的重复业务记录。
5. 员工不能通过资料列表、原件预览或错误提示取得未获授权的内容。

依赖：真实账号与权限上下文、原件标识及保存机制。

## PM-US-02 员工看到提取结果及其出处

对应：PM-REQ-02、04。

作为员工，我希望看到系统从资料中提取出的文字和字段，并能对照出处，以便核对而不必重新翻找原件。

讨论：截图、视频、语音和技术文档的样本与效果不同，分别验证。模型不确定的内容应保留不确定性。

验收建议：

1. 提取结果与正确的原件版本及处理运行关联；能够识别哪些内容来自系统提取。
2. 对已提取字段，能回到相应文字框、文档页或音视频片段；具体定位形式按输入类型确定。
3. 看不清、没有出现或来源冲突的字段，显示缺失或候选，不猜出金额、日期和客户。
4. 一个资料包含多个事项时，不无提示地混成一个业务对象；拆分及归属规则待核实后执行。
5. 处理失败或模型不可用时保留原件与可见任务结果，不把失败标为已确认记录。

依赖：PM-US-01及相应输入提取能力；效果要用真实样本检查。

## PM-US-03 授权人员核对后正式录入

对应：PM-REQ-03、07、08。

作为有确认权限的人员，我希望核对和纠正提取内容后，再由业务系统录入，以便错误识别不会直接改动正式数据。

讨论：谁有确认权限、确认对象是整单还是部分内容、草稿是否持久保存尚待明确；先不替公司选择。

验收建议：

1. 界面能区分待核实内容与正式记录，AI生成JSON不会自行产生正式业务变更。
2. 核对人员可以按已确定规则修改或补充内容，并能查看相关原件证据。
3. 必填、类型、单位、客户匹配及其他已确定业务规则不满足时，不按成功录入处理。
4. 确认时由服务再次核验身份、数据范围与版本；重复确认或网络重试不得重复产生同一正式操作。
5. 操作结果可追溯确认人员、时间、来源和更正内容；取消后的处理和保留遵循最终确定的草稿规则。

依赖：PM-US-02、正式业务对象及确认权限；自动保存草稿的决定仍待答。

## PM-US-04 一笔业务能够关联多份资料

对应：PM-REQ-04、08；其中关联细节为产品建议。

作为员工，我希望查看客户或某笔业务时能找到相关的截图、文件、沟通和时间，以便接手或核实时恢复背景。

讨论：不把上传次数等同业务次数。原件去重、客户去重和业务事实去重分别核实。

验收建议：

1. 已确定的客户、人员、单据及资料关联可以互相回看，仍遵循访问范围。
2. 多份资料支持引用同一已确认业务对象，不因重复截图或视频重叠片段直接重复计数。
3. 业务发生、上传、处理和确认时间按实际含义展示，不把补录时间当原业务发生时间。
4. 不确定属于哪个客户或业务的内容保持待核实，不由AI自动合并正式对象。
5. 改名、交接及纠正后保留必要的历史关联，具体保留规则以公司核实结果为准。

依赖：业务对象、来源标识、人员与时间规则；不要求一次实现全部历史业务模块。

## PM-US-05 员工按编号、关键词或意思查资料

对应：PM-REQ-05、07。

作为员工，我希望用不同方式查找权限内资料，并能打开正确出处，以便不必记住文件名或完整原句。

讨论：相关资料和正式经营事实的查询分开，不把语义相近当成同一客户或真实金额。

验收建议：

1. 已知单号或客户编号按确定的精确匹配规则查询；关键词及语义查询按样本标注检查相关结果。
2. 结果能说明来源、版本、相关片段及必要的上下文，点击后定位到正确原件或业务记录。
3. 文件更正、作废或权限变化后，结果及原件读取按确定的有效版本和访问规则处理。
4. 没有相关结果、资料尚未处理和必要条件不明有合适表达，不用无依据答案补空。
5. 检索服务和AI均不能读取未授权内容；相关性测试与权限测试分别记录结果。

依赖：有效文本与索引、来源定位、权限过滤及代表性搜索样本。

## PM-US-06 老板按需提问并看分析结果

对应：PM-REQ-06、07、08。

作为老板，我希望用文字或语音提出问题，得到可追溯的分析和合适展示，并能继续追问，以便快速了解情况。

讨论：仪表形式不局限于旧软件；语音转写与业务意图理解分别核对，指标定义和来源仍需依据。

验收建议：

1. 语音转成可检查的内容；关键人名、期间或含义不明时，按最终交互规则确认，不擅自猜选。
2. 请求在授权范围内获取数据，已确定的统计由程序计算，AI负责组织分析和展示。
3. 展示包含适用的条件、数据时点及来源，能回到明细或原文；同样定义和数据下结果可核对。
4. 缺资料或定义时说明缺口，不把缺失当作0，也不编造历史趋势。
5. 能按实际结果采用表格、图形或摘要，继续追问仍遵循权限和来源；模型不因一句指令得到正式内容修改权。

依赖：PM-US-04/05中适用的数据与检索路径、业务查询、语音能力及展示协议。不是所有问题都必须经过向量检索。

## PM-US-07 员工和老板通过所有入口遵循一致权限

对应：PM-REQ-07、08。

作为公司授权管理方，我希望权限贯穿业务、资料与AI，以便员工只能访问获准的信息，老板查询也有真实身份依据。

讨论：老板、员工及是否需要其他角色以公司实际为准；技术管理员是否能读业务内容尚未决定。

验收建议：

1. 测试使用经核实的角色、对象和字段范围，分别覆盖允许及禁止情况，不仅验证菜单隐藏。
2. 列表、搜索片段、AI上下文、原件预览、下载、缓存与导出入口应用一致的授权依据。
3. 资料内夹带的指令或JSON中的自称角色，不改变登录身份、访问范围或正式变更权限。
4. 账号停用、交接或权限撤回后的行为按已确定规则核验；旧下载副本的管理边界单独说明。
5. 权限操作及必要访问结果可以按公司确定的审计规则核查，不在日志里无必要复制敏感原文。

依赖：这是其他故事的共同前提，应从最早阶段考虑，不能排到最后补做。

## PM-US-08 纠错后仍能解释数据从哪里来

对应：PM-REQ-04、08；细节为建议。

作为有更正权限的人员，我希望纠正资料或记录时保留来源与必要历史，以便旧报告和新结果的差异可以解释。

讨论：原件替换、识别纠正、业务更正及数据删除是不同操作，权限与保存规则需分别确定。

验收建议：

1. 更正操作依据真实权限执行，AI不能绕过确认自行覆盖正式内容。
2. 原始提取结果与更正文能够区分；来源、版本和必要更正记录按既定规则保留。
3. 更新后的查询与索引能关联有效内容，不继续将已失效片段当作当前事实。
4. 已形成的分析结果能说明当时采用的数据与条件，不暗中替换成另一个版本的解释。
5. 与其他业务数据有关的更正、撤回和删除，按依赖及恢复规则处理，并能核对影响范围。

依赖：版本、来源及审计机制；不是要求所有数据永远保留或禁止合法删除。

## 首次试用建议怎样走查

用同一个脱敏业务案例走完“上传→提取→核对→关联→查询/展示→来源回看”，再补两类失败案例：关键字段无法确定、身份无权查看。记录每步实际看见的结果、是否需人工处理、总耗时和错误。

所有结果在实际运行后才标为通过；本文件没有替代技术台账，也没有新增已经完成的试验。正式验收还需补齐公司规则、原型、样本和阈值，再将故事拆成可实现的小任务。
