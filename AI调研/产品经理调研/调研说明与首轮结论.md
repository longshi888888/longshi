# 产品经理调研｜说明与首轮结论

日期：2026-10-24。  
状态：产品经理方法分析的第一轮草案；没有替代用户核实、技术验证或一周调研。  
用途：把现有需求转成可讨论的产品判断、待验证假设、优先级和验收场景。研究成果与软件源代码在同一项目内分目录保存。

本目录只放longshi自己的产品研究成果，不复制技能本体、通用模板库、演示工程、工具脚本、模型或运行依赖。技能仍在项目外的个人技能目录。研究文档可以按项目GitHub规则版本管理，不因为目录隔离而自动排除；是否包含敏感内容仍需检查。

文档状态使用“草案、待核实、已确认、已替代”。这里的“建议”“候选”“验收建议”不自动升级为已确认需求，也不直接触发开发。

## 2. 本轮实际采用的方法

读取并按本公司需求应用已安装技能：`create-prd`、`identify-assumptions-new`、`prioritize-features`、`prioritization-frameworks`、`user-stories`。它们是指导分析的方法，不是已经执行软件测试的程序。

采用内容：从使用者和工作场景解释价值；区分事实与假设；比较价值、依赖、成本和风险；把需求变成具体可观察的验收行为。

调整内容：把通用模板中的市场细分改为内部使用岗位，把商业上市改为内部试用与迁移，把商业回报改为录入耗时、查询效果、维护成本等；缺少真实样本、人数和工作量时不计算虚构的RICE分数、ROI或交付工期。此前暂存的三个问题仍待答，不再追问以阻塞本轮研究。

## 3. 建议先看的五个产品判断

| 产品判断（建议） | 依据 | 对设计的影响 |
| --- | --- | --- |
| 是否省事，要计算提取加人工核对的总成本 | 用户明确要减少重复录入；当前仅有旧界面OCR观察，尚无真实录入耗时 | 不能只演示识别成功；试用要比较实际完成同一件工作的总耗时和纠错量 |
| 处理进度、资料归属和内容确认是不同状态 | 用户要求多种资料提取与确认；旧系统也有审核和落单等不同状态维度 | 建议分别表达“识别是否完成”“归属是否确定”“哪些内容已确认”，避免一个“成功”掩盖未解决问题 |
| 查资料与算业务数据需要不同结果路径 | 用户同时需要模糊搜索与按需仪表 | 搜索返回相关原文；业务统计使用已确认事实与规则，不能把相似文本命中直接相加 |
| 多份来源不等于多笔业务 | 同一信息可能出现于截图、视频、转发或补充文件；实际比例未知 | 分别识别原件重复和业务事实重复，允许一条业务记录关联多份证据 |
| 第一版宜验证一条完整工作链，而不是堆齐所有旧菜单 | 用户要求一周核实后逐步开发，旧格式均可参考但启用另定 | 候选链为“上传→提取→核对→关联→搜索/分析→回看来源”；范围和首批输入仍待核实 |

这些判断是基于资料的产品建议，不宣称公司目前已经采用相关规则。
