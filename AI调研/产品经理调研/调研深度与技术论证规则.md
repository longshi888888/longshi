# 调研深度与技术论证规则

日期：2026-10-24。  
来源：用户转述专家建议并明确要求严格执行；结合项目README及已有调研。  
状态：本轮新增协作要求；具体功能及技术结论仍按证据逐项确认。

## 1. 先调研，再形成实施规划

用户要求先把功能、细节和遗漏调研出来，再编写规划。继续保留一周持续调研过程；工作次序为：

**收集事实与原件 → 逐项梳理功能及异常 → 核实规则和关联 → 比较技术及调查实际案例 → 验证关键不确定性 → 整理可审阅图纸 → 确认后编写施工规划 → 正式开发。**

当前的需求草案、优先级、数据流和一周工作安排只是帮助发现问题的研究工具，不是已批准的实施方案。研究工作安排可以继续维护，但不得用“先做一个最小版本”作为理由跳过其余功能的调查，不能把候选排名直接变成删减范围或开工指令。

“所有细节”以longshi的实际业务、已有页面与明确新增需求为调查范围，持续补缺，不指无限扩展与公司无关的模块。不得声称能预知所有未来变化。已发现但未讲清的事项必须逐项留下缺口和影响；不得因一周到期就宣告全部完成。

## 2. 功能调查怎样才算深入

每个相关功能逐步查清以下内容；已有资料先引用，缺口按具体案例问，不要求用户一次填写全部问卷：

1. **目的与触发**：谁遇到什么情况，需要完成什么工作，当前如何处理。
2. **输入与字段**：来源、必填/可空、类型、单位、精度、默认值、字典及证据位置。
3. **页面与操作**：录入、查看、搜索、筛选、排序、批量操作、打印/导出等哪些实际需要。
4. **状态与规则**：状态流转、确认条件、计价与舍入、时间口径、审批及生效点。
5. **岗位与权限**：谁看、谁录、谁确认、谁修改、谁交接；字段与附件可见范围。
6. **正常与异常**：缺信息、重复、冲突、驳回、取消、修改、退货、重试等适用情况。
7. **数据关联与生命周期**：与客户、员工、单据、原件、版本、历史、归档和备份的联系。
8. **完成证据**：一笔能走通的案例、对应输入输出、待核实项及可检查的正确/错误行为。

这些是调查维度，并非每个功能都必须拥有全部操作。无关维度标明不适用及理由，不能为了填表新增功能。截图里看得到的格式继续作为参考，不再以是否在用为提取前提。

调查范围见[功能与细节覆盖总表（公开摘要）](../公开接续/功能与细节调研覆盖总表.md)。旧问题Q01—Q21、输入问题IN-01—IN-03和实验EXP编号继续沿用，通过链接关联，避免重复建立互相矛盾的问卷。

## 3. 每项技术建议必须能回答的问题

| 必须说明 | 需要给出的内容 |
| --- | --- |
| 为何需要 | 对应哪项已调查的功能；不采用它会有什么影响 |
| 工作原理 | 输入经过什么处理变成什么输出；数据存在哪里；哪个组件负责哪一步 |
| 职责边界 | 能做什么、不能做什么，哪些事情仍由业务程序或人工负责 |
| 候选比较 | 比较实际可替代路线，必要时包含不引入该组件的简单办法；按相同任务比较 |
| 适用条件 | 系统与版本、网络、资源、并发、文件格式和依赖；未知内容明确待测 |
| 外部证据 | 官方文档、源码/问题记录、项目社区的亲历案例；记录时间、版本与上下文 |
| 成功与失败 | 谁做过、怎样成功、哪里失败、是否修复；未找到时如实写未找到 |
| 公司验证 | 固定样本、对照答案、环境、步骤、结果和失败退路；未做实验不能标可用 |
| 持续使用 | 部署位置、维护、升级、备份恢复、替换路径，以及实际开源/商业功能范围 |

技术论坛用于寻找实际经验。优先读原作者报告、维护者回复和项目官方社区；转载、宣传与匿名结论只能作线索，不能替代原始证据。

证据分开标记：**官方声明、外部用户报告、维护者复现/修复、longshi实测、待核实**。它们不能互相替代。论坛中一个失败不等于当前所有版本必失败，一个成功也不等于本项目成功；问题关闭不自动表示修复已进入选用发行版。

## 4. 遇到方向错误时直接指出

发现建议与公司业务、权限或实际技术能力冲突时，先明确说出“哪一项不成立”，给出原理与来源，再提出可比较的替代方案。适用于我的建议、外部专家意见及技能模板，不按身份照单全收。

例如：

- 不以“开源Office”统称文件读写库、公式引擎、业务列表和在线文档服务器；它们职责不同。
- 不把“AI能生成图表”当作数据与统计规则已具备，不把识别出金额当作成交。
- 不把“源码公开”当作所需全部功能免费，不只根据Star或流行度选型。
- 不把EXE交付理解成数据库、文档服务器和模型必须全部装进每台员工电脑；部署位置需根据实际条件论证。

当无法确定时说明具体不确定条件，安排核查或小实验，不用“确定可以”代替证据。用户提出质疑时，应解释理由并允许证据推翻原方案，不能机械迎合。

## 5. 开始写施工规划之前要有的图纸

以下为交付物要求，尚未完成的保持待调研：

- 功能与细节覆盖清单：所有相关域被检查，范围去留及缺口有依据。
- 正常及异常业务流程、状态与岗位交接图。
- 页面和关键交互草图、字段字典及各类数据之间的关系。
- 角色、业务数据、字段、原件、搜索和AI的统一权限说明。
- 原件—提取文本—JSON草稿—人工确认—正式事实—检索/统计—展示的数据流。
- 组件职责图与比较结论：选什么、为何选、放哪里、如何连接、失败怎么办。
- 关键实验记录、安装与维护条件、迁移和恢复方案、验收案例。

用户逐步审阅后再形成可执行施工计划。仍影响业务正确性、权限、数据完整性或关键组件可行性的缺口，不得在规划中写成已解决。
